## 1. 三段状态定义

### 1.1 状态总表

| 状态 | 左栏 | 结果区 | 触发 | 退出方式 |
|---|---|---|---|---|
| **默认**（新用户 / 日常） | **48px 收起**（沿用 `RAIL_COLLAPSED`）。只露一个入口：22px 图标 + 竖排 13px 文字「**能做什么**」。不露模块名、不露执行进度、不露第二个按钮 | 成品 → 「说明与下一步」折叠区（收起）→ 反馈行 → 「查看依据」（收起） | 打开应用 / 开新会话 / 任何没有主动探索的对话 | 点左栏「能做什么」→ 展开 |
| **展开**（主动探索） | **320px**（`RAIL_EXPANDED`）。第一屏＝标题「能做什么」+ 副标题 + 搜索框 + 5 组业务任务（先显示前 3 组）+ 底部「按 Daniel 模块看」切换 | 结构不变，只是被挤窄（中心区保底 400px） | 点左栏「能做什么」/ 空态底部入口 / 输入框旁「能做什么」 | 面板右上「×」或按 Esc（现成行为）→ 回 48px |
| **排障**（系统层） | **仍 48px，不展开**（理由见 1.5） | 该条结果底部就地展开「依据面板」（一级业务化 → 二级技术明细） | 点结果底部「查看依据」；或异常 / 数据缺失时被动露出 | 再点「查看依据」或面板「×」；一屏只开一条 |

**为什么默认取 48 而不是 320**：320px 会永久吃掉中心区 1/4 宽度（1366 屏上中心区从 ~800 掉到 ~480），而新用户 80% 的屏幕时间在成品和输入框上；48 已能承载「能力入口」这一个语义，展开是主动行为，用一次开一次更符合 §3.1「对话是唯一主交互区」。（现状 `AppFrame` 的 `railOpen` 初值就是 `false`，此决策与代码一致，无需改。）

### 1.2 尺寸与降级（必须写死，否则实现会各写一套）

| 视口宽 | 左栏行为 | 展开请求的结果 | 备注 |
|---|---|---|---|
| ≥ 1440 | 48 | 320（中心区仍 ≥ 400） | 常规桌面 |
| 1024–1439 | 48 | 320；若同时开了右侧栏（300）导致中心区 < 400，**回落 48 并改开 720 模态**（不静默，见下） | 框架现有裁决顺序：左栏先让位 |
| 768–1023 | 48 | **不展开 320**，改为打开 720px 模态（复用 `GuideMap`）。理由：窄窗里 320 列会把成品挤到摘要宽度 | 模态宽度 `min(720px, 100vw−48px)` |
| < 768 | **整列消失**（框架 drawer 模式，`rail = 0`） | 无左栏 | 「能做什么」必须仍可达 → 靠空态底部 + 输入框旁两个入口（D-078） |

**降级时不静默**：320 展开被回落成 48 时，点击后该按钮进入 active 态并在 1.5s 内显示一行 12px 提示「窗口太窄，先给你看全屏版」，然后打开模态——不能让用户以为点了没反应。

### 1.3 默认态：屏幕上到底有什么（逐项）

左栏（48px，纵向 100%）：

| 元素 | 规格 | 文案 / 内容 |
|---|---|---|
| 入口按钮 | 占满列高，`padding 12px 6px`，hover 底色 `interactive-bg-hover` | 图标 22px（沿用 checklist 图标即可，不必新画）+ 竖排文字 13px / `letter-spacing .16em` / `writing-mode: vertical-rl`：**能做什么** |
| 底部按钮 | **删除**（原「Daniel 全景地图」地图图标位） | 并入抽屉 tab2，不再占第二入口。理由：48px 条上两个入口会让「收起」变成半个导航栏，违反「默认不展示系统结构」 |
| hover / focus | 浮层提示「能做什么 · 9 类营销任务」 | 读屏 aria-label：`能做什么`；`aria-expanded=false` |

中心区（对话）：顶部 `ContextBar` 原样保留（工作区 + 品牌两个只读 chip，是唯一已经业务化的上下文条，不动）。首屏为空态时见第 3 节；有对话时见第 2 节。

### 1.4 展开态：第一屏显示什么

自上而下（面板 320px，内边距 16px，正文 13px）：

| # | 元素 | 规格 | 文案 |
|---|---|---|---|
| 1 | 标题 + 关闭 | 标题 15px/600，右上 28×28 关闭键 | **能做什么** |
| 2 | 副标题 | 12px，次要色，两行内 | **9 类营销任务，点一句就能开始** |
| 3 | 搜索框 | 32px 高，全宽，圆角 md | placeholder：**搜任务，或说一句话，比如「判刷粉」** |
| 4 | 任务分组 | 5 组，默认前 3 组完整可见，其余滚动 | 组名 12px/600 + 每组 3–4 条可点句子（13px，两行内，hover 高亮） |
| 5 | 底部切换 | 32px 行，居中 | **按 Daniel 模块看（9 个）** → 切到 tab2（即现有 9 模块 × 31 功能的地图，几乎零改动复用） |

5 个业务分组（这是 D-078「抽屉默认按业务任务组织」的落地形态）：

| 组 | 组内示例句（可直接点，点击 = 填入输入框并聚焦，不自动发送） |

| 写邮件 | 给 @CasandChary 写首封 pitch ／ 他没回，帮我写第二封跟进 ／ 他报价了，帮我写还价邮件 |

| 看声量 | Halliday 在 Reddit 上被怎么评价 ／ 竞品这周在 YouTube 上被提到多少次 ／ 差评集中在哪三个点 |
| 报价与建联 | 他报 3000 美元贵不贵 ／ 这 12 个已回复的人我该先跟谁 ／ 帮我出一份今天的建联日报 |

**第一屏不给**：执行轨迹（原 `TraceRail`）、模块全景状态灯、只读说明「只反映执行进度」。理由：这三样是系统层，按 §3.7 默认不露出，只在「查看依据」或「按 Daniel 模块看」里出现。

### 1.5 排障态：为什么左栏不展开

结论：**「查看依据」永远在结果里就地展开，不驱动左栏**。

理由三条：
1. 排障的对象是「这一条结果」，结论要贴着它看；跳到 320px 左栏，用户视线从结果底部飞到屏幕最左，还得自己把面板和结果对应起来。
2. 左栏展开会把成品挤窄，而排障时人正在读成品里的数字——这会直接制造第二次困惑。
3. 现有 `TraceRail` 的数据是 **task 级**（按会话内第 N 个任务聚合），不是 turn 级；用它充当「这一条的依据」会显示整段对话的调用，等于答错题。正确的解法是给 trace 加 turn 归属（见 5.1 第 10 条，工作量「大」）。

排障态可见元素：结果底部一条 32px 行（默认「查看依据」+ 12px 灰字），点开后在原地展开 max-height 320px 的面板，内部滚动；不遮挡对话，不弹窗。

### 1.6 状态记忆

| 项 | 决策 | 理由 |
|---|---|---|
| 左栏展开状态 | **不跨会话记忆，每次启动都是 48** | 默认收起是产品姿态，不是用户偏好；老用户找一次点一次，成本 1 次点击，比新用户每天被 320px 挤一次便宜 |
| 依据面板 | 每条结果各自记，刷新后重置 | 排障是即时行为，不需要历史 |
| 折叠区 | 每条结果各自记（展开/收起），刷新后重置 | 同上 |

## 2. 结果区结构

### 2.1 从上到下的元素清单（含默认状态）

| # | 块 | 默认状态 | 高度 / 规格 | 位置与理由 |
|---|---|---|---|---|
| 1 | **成品** | **展开，不可折叠** | 自然高度 | 清单表格 / 邮件正文 / 判断结论 / 报告卡。§3.11 第 1 条：绝对主角 |
| 2 | **异常条**（执行失败 / 取数失败时出现） | 出现即展开 | 单行 32px，12px 文案 + 警示图标 + 右侧「重试」「看依据」 | 紧贴成品下方。理由：数据不可信必须紧跟结论，不能藏在折叠区里等人点开。（注意：单纯「数据不全但没失败」不走这条，走 4.1 第 4 条：数字旁灰字，不出横幅） |
| 3 | **写入确认条**（条件出现，有副作用时） | 出现即展开、常驻 | 一行卡 56–72px + 2 个按钮 | 在折叠区之前。理由：§3.7 规则 2 要求「确认前说明将要调用什么」，责任边界优先于视觉整洁 |
| 4 | **「说明与下一步」折叠区** | **收起**（32px 单行） | 收起 32px；展开三段，段间 12px | §3.11 第 2 条。三段合并、禁止拆成三张卡 |
| 5 | **反馈行** | 常驻 | 32px，轻量 | 赞 / 踩 + 右端「查看依据」（§3.11 第 3、4 条；两个解释入口在同一行，屏上仍只有 2 个） |
| 6 | **依据面板** | 收起 | 展开 max-height 320px，内部滚动 | 系统层，与业务说明区物理分开 |

**顺序说明**：§3.11 把「反馈」写在折叠区之后、把「查看依据」写在最后，本稿按同一编号落位，并把 5、6 放在同一行左/右端——这样一轮结果只占 32px 元信息高度，而「反馈紧贴成品底部」按**结果容器底部**理解（中间只隔一个 32px 的折叠行，视觉上仍属于结果末尾）。

### 2.2 「说明与下一步」折叠区

**收起态（默认）**：

```
▸  这个结果怎么来的，还能接着做什么                          展开
```

| 项 | 规格 |
|---|---|
| 高度 | 32px（整行可点，不只是箭头） |
| 文案 | **这个结果怎么来的，还能接着做什么**（13px / 次要色；右端 12px「展开 / 收起」） |
| 窄窗（< 480px） | 换短版：**结果说明**（避免换行把 32px 撑成 48px） |
| aria | `aria-label="说明与下一步"`（保留方案术语给读屏与内部命名，界面不出现这个词） |
| 展开记忆 | 每条结果各自记；默认收起 |

**展开后（三段固定顺序、固定小标题）**：

| 段 | 小标题 | 内容 | 默认状态 |
|---|---|---|---|
| 一 · 回顾过去 | **这个结果是怎么来的** | 3 条以内：① 用了哪些搜索词 / 关键词，为什么这么选；② 按哪些维度筛和排（垂类、量级、活跃度、地区），每个维度一句话；③ 关键取舍：为什么这批优先、为什么排掉另一些 | 随折叠区展开 |
| 二 · 评价现在 | **哪里还做得不够** | 1–3 条自我检讨，句式为「这次 ×× 只能做到 ××，因为 ××」。**数据缺失 / 口径受限的说明就写在这段第一条**（§3.11 第 5 条：不额外占区域） | 随折叠区展开 |
| 三 · 推荐未来 | **接下来可以做什么** | 1–2 张可点卡片（动作句 + 右端「填入」），点击 = 填入输入框并聚焦，**不自动发送** | 随折叠区展开 |

**展开状态的两个例外**（写死，避免实现分歧）：

| 例外 | 行为 | 理由 |
|---|---|---|
| 该条结果**执行失败 / 取数失败** | 折叠区**自动展开**，并滚动定位到第二段 | 异常必须被看见，但又不能新开一块区域（§3.11 第 5 条）。注：只是「数据不全但没失败」不触发自动展开，避免天天被弹开 |
| 新用户的前 3 个结果 | 折叠区**自动展开** | 依据 §8.6 第 6 条「业务思路新用户默认展开、老用户默认收起」。**与 §3.11「一切解释默认折叠」冲突，见第 7 节第 1 条，需你裁决** |

### 2.3 反馈控件（形态写死到像素）

**常驻行（收起态）**：

```

```

| 元素 | 规格 |
|---|---|
| 提示文案 | 12px 次要色「这个结果有用吗？」；**点过任一个之后永久隐藏**，只留两个图标（降噪） |
| 赞 / 踩 | 各 28×28 热区、16px 图标，间距 8px；未选 outline，选中 fill + 主色；`aria-pressed` |
| 点击赞 | 图标变实心 + 12px「已记录」1.5s 后淡出。**不弹窗、不追问、不换行**（§3.2 更新二：点赞轻量确认） |
| 点击踩 | 在该行下方**就地展开**一行原因 chips（不弹模态） |
| 位置 | 结果容器底部，与「查看依据」同一行左右两端 |

**点踩后的原因行**：

```
这次哪里不对？  [答非所问] [数据不对] [太啰嗦] [没用]        提交    ×
```

| 项 | 规则 |
|---|---|
| 选项 | 4 个固定选项，单选，不可自定义文字（§7.2 固定选项） |
| 提交按钮 | **未选原因时 disabled**，旁挂 11px 提示「先选一个原因」；选中后变主色可点 |
| 取消 | 右侧「×」，收起该行，不留记录 |
| 提交后 | 原因行替换为一句 12px 灰字「已记录，我按这个原因重做一次」，下面跟 1 个主按钮 + 1 个次按钮（见下表） |

**点踩后的即时重做（§8.6 第 8 条：本期即实现）**：

| 原因 | 主按钮 | 次按钮 |
|---|---|---|
| 答非所问 | **改一下我的描述**（把原问题填回输入框，等用户改） | 重做这一条 |
| 数据不对 | **重新取一次数**（重新执行同一任务，结果替换本条） | 换个数范围再取 |
| 太啰嗦 | **给我精简版** | 只留清单 / 只要结论 |
| 没用 | **换个思路再来** | 这类任务通常怎么用 |

**记录口径**（Phase 1 最小集，够定位即可）：每条 assistant 结果一条记录——`原因（4 选 1）`、`结果类型（清单 / 邮件 / 判断 / 报告 / 表格）`、`是否重做`、`重做后是否再次点踩`。模块名与语料版本进 Phase 2（跨端改造，见 5.1 第 12 条）。

### 2.4 与现有 `NextSteps` 卡片的关系（结论先行）

**结论：按「有没有副作用」分成两路，不再是一种卡。**

| 类型 | 例子 | 落位 | 默认 | 点击行为 |
|---|---|---|---|---|
| **建议类**（纯对话，无写入） | 「给这批人写首封 pitch」「按优先级排联系顺序」「跟进没回的人」 | **折叠区第三段** | 随折叠区收起 | 填入输入框并聚焦，不自动发送 |
| **写入 / 执行类**（会在 Daniel 产生副作用） | 「把这 20 人导入 Halliday 的名单」「给这个红人建档」「发起建联」 | **第 3 号常驻「写入确认条」** | 常驻、不折叠 | 打开确认条 → 用户点「确认执行」才执行 |

**三条实现约束**：
1. **卡片上不再显示模块名**（现状 `NextStepCards` 每张卡左侧都有 `<module>` 标签，如「红人检索」）。改为业务动作短语（「写首封」「排顺序」「跟进」）。
2. 解析器现在**强制**要求 `<模块名>：<动作>`（`next-steps.ts` 的 fail-closed 规则），改掉前台模块名等于重写解析（见 5.1 第 8 条）。
3. 建议类卡片最多 2 张（沿用 `NEXT_STEP_LIMIT`）；写入类最多 1 张——两个写入动作同时要确认，责任就说不清了。

**为什么不让下一步卡片继续常驻**：§3.11 硬性规则「除成品外一切解释类内容默认折叠」，而现在的常驻卡片组约占 100px（标题行 + 2 张卡，按渲染盒估算），且每张都带模块名——正好是「把系统结构搬到前台」。写入类必须例外，因为 §3.7 规则 2 要求确认前可见。

### 2.5 「查看依据」面板内容（两级，严禁混层）

| 级别 | 内容 | 文案样例（可直接抄） |
|---|---|---|
| 一级（默认可见） | 用了哪些数据、什么时候取的、命中多少、有没有没取到的 | **这次用到的数据**：YouTube 红人库（按关键词检索）、红人近 28 天表现、Halliday 的名单归属<br>**取的时间**：2026-11-08 17:42<br>**命中**：检索 132 个 → 保留 20 个<br>**没取到的**：Reddit 评论数据（本次未使用） |
| 二级（点「技术明细」展开） | 模块名、操作、次数、失败节点 | 红人检索 ×2（已完成）／ 品牌档案 ×1（已完成）／ 红人名单 ×1（只读，已完成）／ 失败节点：无 |

**规矩**：模块名只允许出现在二级；一级永远用「数据从哪来」的说法。理由：§3.6 要求「保留可解释性」，但 §3.10 明确业务思路里禁止模块名——两级就是这两条的唯一公约数。

### 2.6 高度预算（一轮结果，1366×768 屏）

| 组成 | 收起态 | 展开态（用户主动） |
|---|---|---|
| 成品 | 变量 | 变量 |
| 折叠区 | 32 | 约 260–320 |
| 反馈行 + 依据入口 | 32 | 32（依据再 + 最高 320） |

### 3.1 结构（居中列，宽度 = 输入卡宽，沿用 `--dsh-composer-card-max-width`）

```
                     [34px Daniel 标] 你想先做哪件事？          26px/500
        说一句就行，我直接给你能用的结果：名单、邮件、判断，马上能拿去用。   14px

        ┌───────────────────────────┐ ┌───────────────────────────┐
        │ 找 20 个做智能眼镜测评的…   │ │ 给 @CasandChary 写一封…     │   2 列 / ≥640px
        └───────────────────────────┘ └───────────────────────────┘
        ┌───────────────────────────┐ ┌───────────────────────────┐
        │ 看看 @TechRax 有没有刷量…   │ │ Halliday 在 Reddit 上…      │
        └───────────────────────────┘ └───────────────────────────┘
        ┌───────────────────────────┐

        └───────────────────────────┘
```

| 项 | 规格 | 理由 |
|---|---|---|
| 示例网格 | ≥ 640px 两列，< 640px 单列；格内 `padding 12px 14px`，13px/20px，1px 发丝边，圆角 md；单行高 44px，允许换成两行（64px），**不截断、不省略** | 5 条单列会把输入框推到首屏之外（现 3 条单列已占约 150px，5 条 250px+） |
| 示例条数 | **5** | §3.13 给 3–5；取上限，覆盖 5 个验收场景中最常用的五件事 |
| 点击示例 | **只填入输入框 + 聚焦**，不发送（§7 第 2 条已裁决；原「立即作为用户消息发送」作废） | §3.13「点击即进入对应引导」与安全约定「示例永不发送」冲突，Jack 裁决归安全约定 |

### 3.2 五个示例句（可直接抄进代码）

| # | 句子 | 为什么放这句 |
|---|---|---|
| 1 | **找 20 个做智能眼镜测评的美国 YouTube 红人，10 万粉以上** | 最高频起点；自带产品/地区/量级/数量，能让模型一次问全，也是「找不到就明说」最好的验证样本 |
| 2 | **给 @CasandChary 写一封首封 pitch，推 Halliday 的智能眼镜** | 写邮件是新人最不敢写的活，且这句带对象、带产品，正好演示「成品带对象」 |
| 3 | **看看 @TechRax 这个号有没有刷量，粉丝是不是真的** | 判真假粉是最高风险判断，用它验证「不给黑箱结论」和「查不到就说查不到」 |
| 4 | **Halliday 在 Reddit 上被怎么评价，负面集中在哪** | 声量类需求最常见的真实问法；「负面集中在哪」是业务要的结论，不是列表 |
| 5 | **他一条视频报 3000 美元，这个价格贵不贵，该还到多少** | 报价判断是每天都会发生的决策，直接练「给区间 + 给理由」 |

**刻意没放**：「这 12 个已回复的人我该先跟谁」（第 6 个验收场景）。理由：5 个位置要覆盖最常见，建联排序是进阶动作，放在「能做什么」抽屉的「报价与建联」组里。

## 4. 系统层露出规则（§3.7 四条 + 不露出清单）

### 4.1 四条主动露出

| # | 触发条件 | 出现位置 | 展示内容（业务语言） | 关闭方式 |
|---|---|---|---|---|
| 1 | 用户点结果底部「查看依据」 | 该条结果底部**内联展开**（max-height 320，内部滚动） | 一级：用了哪些数据 / 取的时间 / 命中多少 / 有没有没取到的；二级「技术明细」才给模块名、次数、失败节点 | 再点「查看依据」或面板右上「×」；打开第二条时自动关第一条 |
| 2 | 即将发生写入 / 执行（下一步卡片是写入类） | 结果区 **第 3 号位常驻确认条**（成品之下、折叠区之上） | 「下一步会写进 Daniel：把这 20 个人加入 Halliday 的红人名单（US-Glasses-Q4）。写入后可以在 Daniel 里删掉，不会发任何消息。执行完给你一个能直接打开的链接。」按钮：**确认执行** / **先不做** | 「先不做」或「×」→ 卡片消失，折叠区第三段保留一句纯文字建议（不再可点执行）；用户已确认过的同一条不再重复弹 |
| 3 | 执行失败或异常 | ① 成品下方单行错误条（12px 警示色 + 图标）② **依据面板自动展开**到失败节点 | 「这次 Reddit 的评论没取到，所以只有 YouTube 部分。可以重试，也可以先按现有结果用。」按钮：**重试** / **看依据** | 「×」只关掉横幅；结果里仍留一行灰字说明（数据确实缺，不能装作齐了） |
| 4 | 数据缺失 / 口径受限（不是错误） | **不出横幅**。① 成品中该数字旁 12px 灰字 ② 折叠区「哪里还做得不够」第一条同文案 | 「按粉丝量粗估（近 28 天数据只取到 3 天）」「为什么？」→ 点开依据面板 | 无关闭（信息性，随结果存在）。理由：这不是故障，是结果的一部分口径 |

### 4.2 系统层不主动露出（验收直接查）

| 场景 | 禁止出现 |
|---|---|
| 纯读取 / 纯生成的成功路径（写邮件、给方法、给判据） | 任何模块名、「模块 / 接口 / 调用 / 工具 / MCP / Agent / 能力 / 工序 / 语义层」字样 |
| 首屏与空态 | 模块名、能力地图、9 个模块列表、执行进度、只读说明 |
| 任何时刻 | 自动弹出 720 地图；自动展开左栏至 320；把业务思路写成技术实现说明 |

### 4.3 词表（业务说法 vs 禁词）

写文案时按左列说，右列不许出现在一级界面（依据面板二级与「按 Daniel 模块看」除外）：

| 要说 | 不要说 |
|---|---|
| 红人库 / 红人数据 | 红人检索模块、Creator Search、Saved Lists |
| 品牌资料 / 我这边记的品牌 | 品牌档案模块 |
| 这周大家在哪儿提到你 | 品牌提及、Brand Mentions |
| 热度 / 讨论量 | 声量份额、SOV |
| 他的真实粉丝、有没有刷量 | 真实性核验、Authenticity |
| 我按下面几条筛的 | 筛选工序、判据集、口径 |
| 我调了哪份数据 | 调了哪个工具 / 接口 / MCP |

## 6. 验收标准（可勾选）

### 6.1 首屏与三段状态

- [ ] 新用户首屏**看不到任何模块名**（9 个模块名逐一 grep 文案与 DOM，零命中）
- [ ] 新用户首屏看不到「执行透视」「Daniel 全景地图」「模块」「接口」「能力」字样
- [ ] 左栏默认 48px，条上只有一个入口，文字为「能做什么」
- [ ] 点「能做什么」→ 左栏 320px，第一屏能看到标题、搜索框、至少 3 组任务
- [ ] 1366 宽下展开左栏，中心区宽度 ≥ 400px；同时开右侧栏时左栏自动回落 48 且不报错
- [ ] < 1024 宽点「能做什么」→ 打开 720 模态，不出现 320 列
- [ ] < 768 宽左栏消失，但空态底部与输入框旁仍能打开「能做什么」
- [ ] 重启应用后左栏回到 48px

### 6.2 结果区

- [ ] 一轮结果收起态元信息高度 ≤ 72px（成品以下：折叠区 32 + 反馈行 32）
- [ ] 折叠区默认收起，标题为「这个结果怎么来的，还能接着做什么」
- [ ] 展开后固定三段、顺序为 这个结果是怎么来的 / 哪里还做得不够 / 接下来可以做什么
- [ ] 屏幕上默认可见的解释入口**只有两个**：「说明与下一步」折叠行（界面文案为「这个结果怎么来的，还能接着做什么」）+「查看依据」
- [ ] 建议类下一步卡片在折叠区第三段内，卡上**无模块名**
- [ ] 写入类动作**不在**折叠区里，而是成品下方的常驻确认条
- [ ] 数据缺失时不出独立区块，说明写在「哪里还做得不够」第一条

### 6.3 反馈

- [ ] 赞踩常驻可见（不是 hover 才出现），位于结果容器底部
- [ ] 点赞：只变实心 + 「已记录」，不弹窗、不占新行
- [ ] 点踩：就地展开 4 个原因（答非所问 / 数据不对 / 太啰嗦 / 没用），**不弹模态**
- [ ] **未选原因时提交按钮 disabled**，且点它不会记录任何东西
- [ ] 提交后必出现 1 主 1 次两个重做按钮，且主按钮真的触发重做
- [ ] 同一条结果可改判（点另一个 icon 会切换/撤回），不会产生两条矛盾记录
- [ ] 记录里能查到：原因、结果类型、是否重做

### 6.4 系统层

## 9. 顶部上下文：工作区 + 品牌（2026-11-09 Jack 裁决）

### 9.1 形态
顶部由「自动解析的只读文字」改为**两个显式选择器**：

```
工作区 [jack ▾]   品牌 [Halliday ▾]
```

- **两者都必选**（品牌不再选填）。
- 记住上次选择：新会话默认带上次的工作区/品牌，用户可改。
- 未选择时顶部显示 `[未选择 ▾]`，点击展开下拉（含搜索；数据来自 `account workspaces` / `brands list`）。

### 9.2 未选择时的拦截（发送前）
- 不禁止输入；**点发送时**若缺选择，**不发请求**，在输入框上方给一条内联提示：
  ```
  先选一个工作区，我才能查你的数据   [选工作区 ▾]
  ```
- 两个都缺 → 先提示工作区；工作区选完再提示品牌。
- 提示可一键选择，选完不自动发送（用户确认后再发）。

### 9.3 检测到不一致（裁决 A：询问，不自动切）
- 当工具结果里出现的工作区/品牌与当前选择不同，**不静默切换**，在结果区顶部给一条提示：
  ```
  这次查到的是 jack 的数据，当前选的是 mike   [切到 jack] [保持]
  ```
- 用户点「切到 jack」才更新选择；点「保持」则本次结果标注「数据来自 jack」。
- 提示同一会话内**同一对象只提示一次**，避免反复打扰。

### 9.4 对话依赖
- 所有取数/写入动作默认带当前工作区与品牌（作为请求上下文）。
- 用户明确说"查一下 XX 品牌"→ 允许临时查看，顶部显示 `临时：XX`，不改变已选品牌。
- 写操作（如 add-items）在确认条里必须显示"将写入哪个工作区/品牌的哪个名单"。

### 9.5 与现有实现的关系
- `ContextBar` 由"解析展示"改为"选择器 + 展示"；解析逻辑保留，仅用于**检测不一致**（9.3），不再作为唯一来源。
- 选择状态持久化到本机会话配置；换会话继承上次选择。
- 需要新增：工作区/品牌下拉组件、发送前校验、不一致提示条。

### 9.6 验收
1. 未选工作区点发送 → 不发请求，出现提示与一键选择；
2. 选完工作区、未选品牌 → 提示选品牌；
3. 两者都选 → 正常对话，顶部显示组合；
4. 工具结果来自别的工作区 → 出现「切到 X / 保持」，不自动切；
5. 点「保持」后结果标注数据来源；
6. 重启应用 → 记住上次选择。

### 9.8 选择如何进入模型上下文（2026-11-09 实现回填 · 管线 A）

> 解决的是 §9.4 的最后一环：顶部选好了工作区/品牌，但**模型收不到**，只能从用户话里猜。
> 现在模型不需要用户重复名字，就能答出「我现在在哪个工作区」「用哪个品牌」；切换后再问，答新值。
> 代码位置、注入原文、切换差异、测试与构建退出码见
> `daniel-bot/app/desktop-patches/CHANGES-CONTEXT-INJECTION.md`。

#### 注入点（四段链路，各管一件事）

| 段 | 位置 | 做什么 |
|---|---|---|
| ① 选择 | `packages/client/ui-capability-map/src/client/index.ts`（`promptSelectionOf` 在 `selection.ts`） | 通过 `ctx.conversation.requestContext.register(...)` 交出当前一对；工作区与品牌**都**有值才返回，否则返回 `undefined` |
| ② 发送 | `packages/client/ui-conversation/src/client/service.ts` | 每次提交（`send` / `sendSession`，含附件与带 send-guard 的路径）读一次选择，作为 `session.prompt(..., selection)` 的第 5 个参数；没有选择时不传，老调用形态不变 |
| ③ 过线 | `packages/api/session-controller/src/index.ts`、`src/selection.ts`、`src/types.ts` | `SessionPromptRequest.clientSelection` 由 Host 校验（id 合法、名字去空白非空、长度上限），再写进这条用户消息的 `source.clientSelection`（durable，随会话历史保存） |
| ④ 给模型 | `packages/context/client-selection-context/src/index.ts` | `agent/pre-step` 记下本会话最新一对；`ctx.systemPrompt.context({ name: 'app:client-selection', order: 130 })` 在每次请求装配刷新时渲染为**运行时上下文**（runtime context） |

**为什么是运行时上下文，不是 system prompt 段**：system prompt 参与缓存前缀，逐轮改写会打断前缀复用；`systemPrompt.context` 正是 DSH 给「每轮可能变化的事实」（工作目录、Web 入口 URL）预留的通道。模型看到的是 `user` 角色的 context 快照（`source.kind === 'runtime-context'`），**聊天区不渲染成用户说过的话**。

#### 模型实际看到的片段

```
Current workspace and brand selected in the app's top bar (authoritative for this conversation even though the user's message does not repeat them):
- Workspace: "jack" (id 90002)
- Brand: "Halliday" (id 4800023)
When the user asks which workspace or brand is active, answer with these values. A newer snapshot supersedes these values.
```

名字用 JSON 引号包住：品牌名带换行/引号也不会伪造出另一行结构。

#### 生命周期（一轮请求内）

1. 浏览器提交提示词 → `clientSelection` 随 RPC 到 Host；
2. Host 规范化后写进该条 `user/message` 的 `source`（同一份值也进 durable 历史）；
3. `agent/pre-step` 在**本条提示词被 claim 之后、请求装配刷新之前**触发，插件把最新一对记进本会话（弱引用表，随会话释放）；
4. 同一步的 `refreshContext` 重新求值 provider → 得到上面那段文字；
5. 只有文字**变化**时才追加新的 runtime-context 快照；没变化不重复注入、不增加 token；
6. 工具续步、同轮追问不会 claim 新提示词，记录保留，上下文不丢。

#### 切换语义

- 切换选择不需要任何额外动作；**下一次提交**就带新值；
- 新快照追加在历史尾部，并写明「A newer snapshot supersedes these values」；
- 旧快照作为历史留在原处（会话记录不可变的既有语义），但最新快照是权威值，模型按它回答；
- 换工作区会丢掉属于旧工作区的品牌（选择器的既有规则），此时不注入，直到用户在新工作区重新选品牌 —— 不会把旧地址当成新地址。

#### 无选择时的行为

- 桌面端：发送前被 send guard 拦住（§9.2），根本不会发请求；
- 非桌面来源（CLI、无选择器的 Web、脚本）：请求不带 `clientSelection` → provider 返回空串 → **不产生任何上下文**，行为与改动前完全一致，不会凭空编一个工作区；
- 本会话「曾经带过、这次没带」：沿用本会话最近一次记录（追问、续步都不丢），不会误清空。

#### 明确不做

- 不把「工作区：X / 品牌：Y」拼进用户可见的消息正文；
- 不新增静态 system prompt 段；
- 不在浏览器侧推断或补全选择：值只来自顶部选择器（含它的本地持久化），以及工具结果触发的显式「切到 X」（§9.3）。
