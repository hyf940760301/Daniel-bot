## 2. 八阶段 × 交付物 × 门禁

| 阶段 | 交付物（缺一不可） | 门禁（过不了不进下一阶段） |
|---|---|---|
| S1 需求梳理 | 需求条目表（**8 列**：编号／原始诉求／目标／输入／输出／明确不做／依赖／风险）＋ **大纲逐条对照表** ＋ 待澄清清单 | ① 每条需求都有"不做"的边界；② 每个待澄清项说明"不答会怎样"；③ **大纲每一块都能映射到需求编号**（缺一块即不通过）；④ 8 列缺一即不通过 |
| S2 方案设计 | 方案文档（架构图／数据流／模块划分／接口契约） | 每个设计选择写明"为什么是它、否掉的备选是什么" |
| S3 架构评审 | 评审记录（逐条结论：通过／改／否） | 未通过项必须有处置结论，不许挂起 |
| S4 风险评估 & 兼容校验 | 风险表（概率／影响／触发条件／规避／回退）＋ 兼容性矩阵 | 每条风险有回退路径；兼容性覆盖旧版本与旧数据 |
| S5 分步落地开发 | 代码 + 每步提交 + 每步自检结果 | 每步可独立回退；不许"一大坨提交" |
| S6 阶段自检 & 质检 | 自检报告 + 质检员报告（问题清零） | 质检员未清零不许交付 |
| S7 阶段交付 & 确权 | 交付说明（改了什么／怎么验／怎么退） | 用户明确确认 |
| S8 归档 & 文档沉淀 | 版本说明 + 决策记录（ADR） | 与代码同提交 |

**阶段不可合并、不可跳跃。** 上一阶段未获用户确认，下一阶段不开工。

## 2.5 常设检查：配置参数必须有消费方（假能力防线）

**由来**：管线 B 的 S1 连续抓到三次同类问题——需求里引用的配置参数，代码里根本没人读：
`channels`（舆情渠道）、`daily.schedule`（每日定时）、周报窗口（写死字面量）。

| 规则 | 做法 |
|---|---|
| 引用即举证 | 需求/方案里每引用一个配置参数，必须写明「谁读它」：文件 + 函数（或明确标"无消费方"） |
| 无消费方 = 两选一 | 要么从需求中删除，要么升级为**显式待实现项**并给排期 |
| 界面不得假装 | 参数无消费方时，界面不许出现对应控件（点了不生效比没有更伤信任） |
| 定期反扫 | S2/S6 各做一次"配置项 → 消费方"全量对账，输出表格 |

## 3. 质检员机制（独立实例）

| 项 | 规则 |
|---|---|
| 角色 | 独立 agent 实例，**与被审对象不是同一个实例** |
| 覆盖 | 方案 / 架构 / 工程 / Agent 能力 四个维度 |
| 时机 | 每个阶段交付物完成后、交用户之前 |
| S1 专项 | 必须逐块核对"需求大纲 → 需求编号"映射，缺块直接 FAIL |
| 输出 | 判定（PASS／FAIL）＋ 缺陷清单（问题／证据／影响／修法），**不许只说"看起来没问题"** |
| 权限 | 只能出缺陷，不许直接改被审文件 |
| 红线 | 有未清缺陷 ⇒ 不得交用户；用户不应承担查漏工作 |
