# 三条线隔离规则（管线 A / 管线 B / 文档）

> 目的：三个任务各自开专用子代理，互不读写对方的文件，避免上下文串味与并发覆盖。

---

## 一、三条线各自的边界

| 线 | 专用代理 | 只能写 | 只能读 | 禁止 |
|---|---|---|---|---|
| **管线 A（桌面应用）** | A 代理 | `/tmp/dsh-build/dsh-src`（代码工作树）、`daniel-bot/app/desktop-patches/`、`daniel-bot/app/tests/` | 任意 | 改飞书文档、改管线 B 仓库 |
| **管线 B（workflow 网页）** | B 代理 | B 仓库工作树、`docs/workflow-ui/` | 任意 | 改管线 A 工作树、改飞书文档 |
| **文档（更新说明 / 方案）** | 文档代理 | **仅飞书文档**（`lark-cli docs +update`） | 任意（代码、变更说明、决策记录） | **改任何代码、任何仓库文件** |

补充：
- **文档代理不读代码细节**，只读：现有文档、变更说明（`CHANGES-*.md`）、决策记录（`DECISIONS-A.md`）、以及总监给的要点；
- **A/B 代理不碰文档**：需要改文档时，由总监把要点交给文档代理。

---

## 二、文档代理的固定简报（每次开新实例时原样粘贴）

```
你是「Daniel Bot 更新说明」的专职文档编辑。任务边界：
1. 只改飞书文档（https://tvo7pfzu3em.feishu.cn/wiki/Drx6wwaUZi8VLbkXiWwceQE8nsg），
   用 lark-cli docs +update 写入；不改任何代码、任何仓库文件。
2. 不新增模块、不调整章节结构，除非总监明确要求。
3. 写作规则（来自用户裁决，必须遵守）：
   - 每个模块：一句判断（总）→ 具体场景/痛点（分）→ Bot 接管了什么 → 一句边界或对比；
   - 说清「为什么做、痛点在哪、价值是什么」，不写"我们的判断"式自述；
   - 不用"代价"这类我方视角的词，改用"用户会遇到什么"；
   - 删除 AI 味句式：总结式收尾（"下面按顺序讲…"）、口号式提炼（"从 X 变成 Y"）；
   - 标题直说是什么+解决什么，不用"为什么/如何"需要读者翻译的句式；
   - 引用用户原话必须真实；没有原话就写"典型问题"，不假装是原文；
   - 数字要具体（91 条命令 / 9 个模块 / 51 个动作 / 11/11 对账）；
   - 安全章只写已验证的事实，边界要明说（同目录密钥挡不住同用户攻击者）。
4. 改完必须回读校验（lark-cli docs +fetch），并报告 revision_id 与改动点。
5. 图片位用「【图 N · 说明】」占位，编号连续；不要自己插图。
```

---

## 三、并发约束（避免上次那种冲突）

| 场景 | 规则 |
|---|---|
| 两个代理要改同一个包 | **不允许**；由总监排序，先完成后一个 |
| 一个代理改 src、另一个改同包 tests | **不允许并行**（会出现中间态类型错误） |
| 文档代理与代码代理并行 | 允许（不同介质），但文档里不得声称"已完成"未落地的功能 |

---

## 四、落地检查（总监每次开工前）

1. 这个任务属于哪条线？→ 选对应代理；
2. 它要写的路径，是否在本线边界内？→ 不在就改派；
3. 与另一条线是否有文件重叠？→ 有就串行；
4. 文档代理的产出是否引用了"未落地的功能"？→ 引用前先确认代码已合并并通过门禁。
