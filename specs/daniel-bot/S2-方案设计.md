## 0. 一页结论

| # | 主张 | 一句话理由 | 详见 |
|---|---|---|---|
| 1 | **Electron 薄壳，复用 Electron 自带 Node 跑 DSH**（D-017）；壳里零业务判断 | D-017 已裁；Electron 主进程可 `ELECTRON_RUN_AS_NODE=1` 起 DSH，省一套 Node | §1 |
| 2 | **业务判断唯一落点是 CLI**；插件只剩"schema／argv／透传／清洗"＋**env 白名单** | 与 S3 同一条线；`{...process.env}` 会把宿主凭据透给 CLI 与仪器 | §1.2、§5 |
| 3 | **宿主层新增"凭据适配器"（一期必做）**，替换 DSH 的明文凭据库 | `settings-models` 明说 API-key 编辑始终可用，Config 关不掉；唯一解是换 store | §3.8 |
| 4 | **内容按仓库形状进包**，但**只带正向白名单**（skills／roles／examples public） | 内部事故/复盘与客户合同不能随包；白名单比黑名单可审计 | §4.2 |
| 5 | **版本绑定＝内容哈希清单 ＋ 版本号 ＋ 与"最新发布"比对**；编号 **C21/C22**（C20 归 S3） | 仓库不是 git、a-v2 不跟踪 docs/marketing ⇒ commit 定位不到包内字节；无签名只能防损坏 | §2 |
| 6 | **Key 根＝系统钥匙串随机主密钥，设备自动解锁、不做 PIN**（D-017）；**登录与密钥可用性拆开** | 登录是 app 门禁，密钥可用性是设备解锁 | §3 |
| 7 | **Electron ad-hoc 签名 ＋ hardened runtime entitlements ＋ 未公证 `.dmg`**；更新留二期 | Electron 的 Helper/Framework 都要逐个签；`--options runtime` 不给 JIT 权限会崩 | §4.9 |

**三条"不这么做会怎样"**

1. **端内校验通过、仓库已变** ⇒ 用户把"绿"当成"对"，比不校验更危险（§2.7 有本轮实测的同类：`next` 的 23/47 范例里 22 条是绝对符号链接，包外不存在）。
2. **Key 明文** ⇒ 备份盘/同步盘即泄露；DSH 自带 `.credentials.yaml` 就是明文，且优先级高于环境变量（§3.8）。
3. **业务判断留在宿主层** ⇒ 换宿主即重写；`clarify.js` 已由 S3 下沉为 53 行薄适配，但 `normalize.js`（54 KB）与 `trace.js` 仍在宿主层（S1 判据 1 仍未完全满足）。

### 1.4 运行时启动时序（Electron main）

```
用户双击
 ├─1 单实例锁（第二个实例只激活已有窗口）
 ├─2 读 app-state.json（上次校验/崩溃计数）；安装期校验（§2.4）
 │     └─ 失败 → 诊断页；不进入能力层
 ├─3 从 Keychain 取 MK（设备已解锁则自动；拒绝/缺失 → "密钥不可用"状态）
 ├─4 管理员登录（app 门禁；与 MK 是否可用**无关**，§3.7）
 ├─5 组装子进程 env（白名单）：
 │     DSH_HOME / DANIEL_HOME / PATH / LANG / TMPDIR
 │     DSH_TELEMETRY_MODE=DISABLED / DSH_TELEMETRY_DISABLED=1
 │     DANIEL_VAULT_SOCKET / DANIEL_VAULT_TOKEN（适配器用；不进 CLI）
 ├─6 起 DSH：ELECTRON_RUN_AS_NODE=1 <Electron 可执行> dsh/lib/bin.js \
 │     --profile web --no-open --port 0
 │     └─ 15s 无 `dsh web: <url>` → 杀进程、抓日志、报错（附路径）
 ├─7 WebView 载入 URL（只允许 loopback；外链交系统浏览器）
 └─8 运行期校验（C1–C4/C10/C18/C21/C22）→ 顶部横幅
```

**就绪契约**：`dsh web:` 行是唯一就绪信号（DSH 文档口径）；`--port 0` 由 OS 选端口，壳解析、不写死。**遥测**：base 组合的 `session-telemetry-otel` 默认 `FEEDBACK_ONLY`，会在"用户反馈"后把会话日志发往 `dsh-otel-collector.deepseeksvc.com`；而 `DSH_TELEMETRY_MODE=DISABLED`（base patch 读该 env）与 `DSH_TELEMETRY_DISABLED`（任意非空则硬禁该行）都能关。app **两个都设**，并在验收里查"无外连"（§4.8）。

### 1.4.1 一次任务的数据流

```
1. 用户原话 → WebView → DSH 会话（模型）
2. 模型调 daniel_clarify → 插件 argv → CLI `clarify plan --json` → 缺项[]/选择面[]
3. 用户回答 → 模型再调 → CLI `clarify ask` → 追问[]/未确认项[]（判断全在 CLI）
4. 模型调读侧工具 → CLI 访问 Daniel 平台 → 缓存在 DANIEL_HOME → 插件 clean() 透传
5. 交付：CLI 出件到工作区 → 返回编号＋核验地址 → 插件清洗 → 界面可点
6. 写操作：CLI 干跑 → 插件落 plan → 壳确认卡 → 人工点击 → 插件 commit
   → CLI `--confirm` 真执行 → 回读 → 审计
```

业务判断只在 2/3/4/6 的 **CLI 内**；插件只搬字节；壳只在第 6 步出现一次。

### 1.6 接口契约

**C-1 壳 → DSH（进程）**

| 项 | 值 |
|---|---|
| argv | `[<Electron 可执行>, <Resources>/dsh/lib/bin.js, --profile, web, --no-open, --port, 0]` |
| env（**白名单**） | `PATH`、`HOME`、`LANG`、`LC_ALL`、`TMPDIR`、`DSH_HOME`、`DANIEL_HOME`、`DANIEL_NO_OPEN=1`、`DSH_TELEMETRY_MODE=DISABLED`、`DSH_TELEMETRY_DISABLED=1`、`DANIEL_VAULT_SOCKET`、`DANIEL_VAULT_TOKEN`、`ELECTRON_RUN_AS_NODE=1` |
| cwd | 工作区目录（DSH 默认 workspace root） |
| 就绪 | stdout 行 `dsh web: <url>`（15s 超时） |
| 退出 | SIGTERM → 10s → SIGKILL；退出码与末 200 行日志写 app-state |

> **注意**：`ELECTRON_RUN_AS_NODE=1` 让 Electron 以纯 Node 运行；原生模块（`node-pty`／`@img`／`sherpa-onnx`）必须按 **Electron 的 ABI** 重建（`@electron/rebuild`），构建期冒烟不通过就不出包（§8-Q4 是兜底）。

**C-2 壳 → 插件（配置）**：`profile/web/cordis.patch.yml` 插入 `id: daniel`，字段用插件现有 Config（`entry`／`python`／`danielHome`／`timeoutMs`），`entry` 钉死 `bundle/data/daniel-cli/bin/daniel`；打包版不接受任意路径覆盖，开发模式才允许并显示 `DEV` 徽标。

**C-3 壳 ↔ 凭据适配器（Unix socket）**

| 项 | 约定 |
|---|---|
| 路径 | `<App Support>/DanielBot/ipc/vault.sock`（0600；启动前删除陈旧的） |
| 认证 | 启动时生成 32B 随机 token，只经 env 传给 DSH；每个请求带 token；校验失败即断开 |
| 协议 | 一行 JSON 请求 → 一行 JSON 响应；`{op, ref\|key, value?}`；响应 `{ok, value?, error?}` |
| 方法 | `resolve/describe/set/unset` ＋ `readRecord/describeRecord/listRecords/modifyRecord/deleteRecord`（与 `ctx.credentials` 同名同语义） |
| 失败语义 | `VAULT_UNAVAILABLE`（socket 不在/超时）、`VAULT_DENIED`（Keychain 拒）、`UNSUPPORTED`（记录类未实现时）——**绝不回退明文** |

**C-4 语料 ↔ 门禁（包内入口）**：`bundle_verify.py --gate=install|runtime --json`、`route_capability.py --check|--query --json`、`capability_gate.py --only=C1,C2,C3,C4,C10,C18`、`daniel --self-test`。

**C-5 版本/清单**：`VERSION.json` 与 `BUNDLE-MANIFEST.json` 字段见 §2.3。

## 2. 必答（a）：端内仪器与仓库版本绑定机制

### 2.1 三种"不一致"，处置完全不同

| # | 不一致 | 例子 | 能否离线判定 | 误判后果 |
|---|---|---|---|---|
| A | **包内文件 ≠ 清单**（缺/被改/符号链接逃逸） | 仪器被替换、范例只剩链接 | ✅ 能（逐文件哈希） | 端内跑的是"另一个东西" |

## 3. 必答（b）：Key 与管理员密码的加密方案（D-017 版）

### 3.1 威胁模型（先说不防什么）

| 威胁 | 一期是否防住 | 说明 |
|---|---|---|
| 备份盘/同步盘拿到 `secrets.enc` | ✅ | 没有 Keychain 里的 MK 解不出 |
| 安装包被逆向拿到 Key | ✅ | 包内**无 Key**；凭据扫描进构建门禁 |
| 日志/崩溃报告泄露 | ✅（纪律） | 只记键名/状态；关 core dump |
| 同事临时用电脑 | ✅ | 登录 ＋ 闲置锁屏 |
| **同机同用户恶意进程** | ❌ **防不住** | 能读进程内存、能连 0600 socket；本地应用边界 |
| Keychain 被锁/拒绝 | ⚠️ 可用性 | 进"密钥不可用"状态；可用恢复密码兜底（§3.9） |

> 目标：**静态存储不落明文**（D-012 底线），不是"抵抗本机 root/同用户攻击"。

### 3.2 裁决与方案（D-017 Q4）

| 项 | 结论 | 为什么 | 否掉的备选 |
|---|---|---|---|
| **密钥根** | **macOS 系统钥匙串**：随机 32B 主密钥（MK）存 Keychain，设备登录后自动解锁，**不做 PIN** | D-017 已裁；MK 不落文件，用户无感 | ① 密码派生 KEK（v1 方案，已否：冷启动必输密码）② 明文/固定密钥（D-012 违规）③ PIN 解锁（D-017 明确不做） |
| **管理员密码** | 仍保留本地账号（A-D12），但**只是 app 门禁**，**不是密钥根** | 登录与密钥可用性拆开（复审 #2） | 用 macOS 系统账号代替（要读系统密码，不可行） |
| **加密** | AES-256-GCM（Node `crypto`） | Electron 主进程标准库 | 三方库（多一个原生依赖，未签名阶段更脆） |
| **KDF** | scrypt（N=2^17,r=8,p=1）只用于两处：**登录验密码** 与 **恢复包裹**；**日常解 MK 不走 KDF**（Keychain 直取） | 日常解锁靠设备；KDF 只在"证明是本人/恢复"时跑一次（~1s） | 用 KDF 派生 MK（＝v1 的密码根，D-017 否） |

**Keychain 实现**：优先 `kSecClassGenericPassword`（service `com.danielbot.vault`、account `master-key`），通过 `keytar` 或 `security` CLI 封装在 `KeychainStore` 接口后；若 ACL 在 ad-hoc 签名下不稳，可切到 Electron `safeStorage`（同样是 Keychain 根）而不改上层。**已知代价**：ad-hoc 签名下重装/重建可能触发一次"允许访问钥匙串"的系统弹窗；用户点"始终允许"即可，文档要写清（§3.10-R1）。

### 3.3 密钥层次

```
Keychain（系统）
  └─ MK = 32B CSPRNG（设备级，登录后自动可读；不做 PIN）
        │ HKDF(info="danielbot/vault/v1")
        ├─ KEK_vault ── AES-256-GCM(AAD="danielbot/secret/<name>/v1") ── records[]
        └─ （可选恢复）KEK_recovery = scrypt(管理员密码, salt) ── wrap(MK)
```

**"密钥从哪来"一句话**：**MK 来自系统钥匙串**（随机生成、只有 Keychain 能取）；**文件里只有密文**；管理员密码**不参与日常解密**，只在"恢复/换机"时用来解一把 MK 的备份包裹（默认开启，可关闭）。

### 3.4 存储格式（两个文件）

`auth/account.json`（只回答"密码对不对"，无密文）：

```json
{
  "v": 1,
  "username": "jack",
  "kdf": "scrypt", "params": { "N": 131072, "r": 8, "p": 1, "dkLen": 32 },
  "salt_b64": "…16B…", "verifier_b64": "…32B…",
  "attempts": { "fail": 0, "locked_until": null },
  "created_at": "2026-11-01T10:00:00Z"
}
```

`vault/secrets.enc`（只有密文）：

```json
{
  "v": 1,
  "mk_wrap_recovery": { "nonce_b64": "…", "ct_b64": "…", "aad": "danielbot/mk/v1|recovery", "enabled": true },
  "records": [
    { "name": "DANIEL_MODEL_API_KEY", "nonce_b64": "…", "ct_b64": "…",
      "aad": "danielbot/secret/DANIEL_MODEL_API_KEY/v1", "updated_at": "…" },
    { "name": "llm-pi-ai/openai-codex", "kind": "record", "nonce_b64": "…", "ct_b64": "…",
      "aad": "danielbot/record/llm-pi-ai/openai-codex/v1", "updated_at": "…" }
  ]
}
```

**铁律**：96-bit 随机 nonce，每次写入换；AAD 绑定"记录名＋版本"；tag 16B 追加在 `ct`；`0600`/`0700`；禁止固定盐/固定 IV/base64 冒充加密/把 MK 写进 plist。

### 3.5 管理员密码怎么存（不再是密钥根）

| 项 | 结论 | 为什么 |
|---|---|---|
| 存什么 | 只存 verifier（scrypt 输出经 HKDF 域分离后的 32B） | 不可逆；域分离防 verifier 当 KEK |
| KDF | scrypt（N=2^17,r=8,p=1） | Node 标准库、零依赖；Argon2id 列二期（算法版本字段可迁移） |
| 盐 | 每账号 16B CSPRNG | 防彩虹表 |
| 比较 | 常量时间 | 防计时侧信道 |
| 限速 | 1s→2s→4s…，10 次锁 5 分钟（计数写 `account.json`） | 只防本地瞎试；防不了拷走文件的离线爆破（诚实） |
| 密码策略 | ≥10 字符；不强制符号 | 长度是唯一有效熵来源 |
| 重置 | **允许本地重置**：能取到 MK（Keychain 可用）即证明是本机所有者 → 删 `account.json` 重建 | 密钥不受影响；不需要"忘记密码就丢 Key"（§8-Q2） |

### 3.6 首次启动

```
1. 无 account.json/vault → 向导
2. 建管理员（用户名 + 密码 ≥10 + 确认）
3. 生成 MK（32B）→ 写 Keychain；生成 vault/secrets.enc；可选"恢复密码包裹"（默认开）
4. 填模型 Key（可跳过，稍后在 Web「模型」页填）→ 经适配器写 vault
5. 安装期校验（§2.4）→ 失败 → 诊断页
6. 起 DSH（env 白名单，无模型 Key）→ 主界面
7. 全程零网络（除用户点"检查更新"）
```

### 3.7 登录 vs 密钥可用性（复审 #2 的核心）

| 状态 | Keychain | 管理员登录 | 能力层 | 用户看到 |
|---|---|---|---|---|
| 正常冷启动 | 可读 MK（设备已解锁） | 需输密码 | 可用 | 登录页 → 主界面 |
| 已登录、Keychain 被锁 | 读不到 | 保持登录 | **模型功能禁用** | 黄条"密钥不可用：解锁钥匙串或点重新授权" |
| Keychain 拒绝（ACL 变） | 拒绝 | 可登录 | 禁用 | 红条 ＋ "重新授权"（重建 Keychain 项需恢复密码/重填 Key） |
| 未登录 | 可读但 UI 不暴露 | 未登录 | 不可用 | 登录页 |
| 换机/重装 | 无 MK | 可建新账号 | 禁用直到导入/重填 | 向导"导入备份或重填 Key" |

> **读工具是否可用**：模型 Key 缺失时模型本身不可用，"能聊天"也做不到；应用仍可打开设置、诊断、导出日志。**不用"降级到无模型模式"这种模糊说法**。

### 3.8 凭据适配器（一期必做，复审 #3）

**为什么必须做**：`dsh-client-ui-settings-models` 的 Config 只有 `credentialOnboarding`（只抑制引导）；README 原文："Models settings and **explicit API-key editing remain available**" ⇒ **关不掉**写入口。而 `dsh-credentials-local` 把 Key **明文**写 `<DSH_HOME>/.credentials.yaml`，且优先级"存储值 > 环境变量"（会覆盖注入）。⇒ 不换 store，D-012 必破。

**方案**：

| 项 | 设计 |
|---|---|
| 组件 | 新插件 `daniel-credentials-vault`（宿主层 glue，**不是业务逻辑**），在 app profile 里**禁用** `dsh-credentials-local` 并挂载它 |
| 实现 | 实现 `ctx.credentials` 的全部方法（`resolve/describe/set/unset` ＋ `readRecord/describeRecord/listRecords/modifyRecord/deleteRecord`），全部转发到 §1.6-C3 的 socket |
| 存储 | 壳持有 MK、负责加解密；适配器**不落盘任何值**，只在内存中短暂持有 `resolve()` 返回值 |
| 失败 | `VAULT_UNAVAILABLE`/`VAULT_DENIED`；**绝不回退明文**、绝不回退环境变量（环境里也没有） |
| 记录类 | 一期全实现（记录就是加密条目，成本低）；避免 OAuth 类 provider 静默坏掉 |
| 验收 | 在 Web「模型」页填一个假 Key → 磁盘上 `.credentials.yaml` **不存在**、`vault/secrets.enc` 多一条密文；重启后 `describe` 仍 configured；`resolve` 能取回（内存） |

**模型 Key 的完整路径（v2 已无 env 注入）**：

```
Web「模型」页输入 → settings-models → ctx.credentials.set(ref, key)
  → 适配器 → socket → 壳 AES-GCM 加密 → vault/secrets.enc
模型请求 → 模型插件 → ctx.credentials.resolve(ref) → 适配器 → socket → 壳解密 → 仅返回给该调用
```

**同时必须做的两件事**：

1. **插件 spawn CLI 用 env 白名单**（复审 #3）。S3 已落一半：`baseEnv()` 会按一张**硬编码名单**（`SECRET_ENV`：DEEPSEEK/OPENAI/ANTHROPIC/… 21 个变量名）删 Key，并有 2 个调用点走它；但 **`startWorker()` 与 `runLive()` 仍用 `{ ...process.env }` 裸透**（实测 3 处 spread：`index.js:55/299/357`）。且"按已知名字删"对新 provider（名单外的新 Key 名）无效。v2 要求：
   - **所有 spawn 点统一走一个 `baseEnv()`**（不许再有裸 `{...process.env}`）；
   - 从"删已知名单"改为 **`allowlist ＋ 后缀剥离`**：只传 `PATH/HOME/LANG/LC_ALL/TMPDIR/DANIEL_HOME/DANIEL_NO_OPEN`，并对所有变量名按后缀 `_API_KEY`、`_TOKEN`、`_SECRET`、`_KEY`（白名单例外 `PATH` 等）以及前缀 `DANIEL_BOT_*`、`DANIEL_VAULT_*` 一律剥离；
   - 加自检：源码里 `...process.env` 出现次数必须 = 1（就在 `baseEnv` 里）。
2. **壳给 DSH 的 env 也不含模型 Key**：Key 只经 socket 流动；因此"Key 只在壳与基座之间"仍成立，且**CLI/仪器完全看不到**。

### 3.9 轮换、恢复、换机

| 场景 | 行为 |
|---|---|
| 换模型 Key | 新记录覆盖同名（新 nonce）；旧密文不可恢复 |
| 换管理员密码 | 只重算 verifier；**MK 与记录不动** |
| Keychain 项丢失/拒绝 | 用"恢复密码"（管理员密码）解 `mk_wrap_recovery` → 重建 Keychain 项；若恢复也关/忘 → 重填 Key |
| 换机 | 导出 `vault/secrets.enc` ＋ `account.json` ＋ 管理员密码 → 新机导入时用恢复密码解 MK → 重建 Keychain 项 |
| 导出备份 | 默认不含明文；备份文件本身就是密文（仍需密码） |
| 关闭恢复 | 设置里可关；关了以后 Keychain 丢＝重填 Key（明确告知） |
