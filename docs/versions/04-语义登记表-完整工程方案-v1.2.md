## 0. 一句话

工序层已有 94 道工序，但它引用的判据（阈值、口径、表达规则）全是散文。语义登记表把这三样变成机器可查的登记项，**让工序与契约去引用它**——不新增层、不新增工具、不新增能力束。

## 1. 口径层：先和实测对齐（v1.2 最大的修正）

### 1.1 实测样例（真实红人，2026-10-29）

`@CasandChary`（Cas and Chary XR，美国，18.6 万订阅）：

| 范围 | 视频数 | 平均播放 | 平均点赞 | 互动率 | 样本说明（工具原文） |
|---|---:|---:|---:|---:|---|
| 整体 | 13 | 3,837 | 71 | 2.21% | 近 28 天 · 13 条 |
| 长视频 | **4** | **53,003** | 1,266 | 2.41% | **最新 30 条 · 4 条** |
| 短视频 | 11 | 3,119 | 71 | 1.86% | 近 28 天 · 11 条 |

### 1.2 由此确认的三件事

| # | 事实 | 对方案的影响 |
|---|---|---|
| 1 | 工具返回的是**平均播放（均值）**，不是中位数 | v1.1 把默认口径写成"中位数"是错的，必须改 |
| 2 | 三个范围的**窗口与取样规则不一致**（整体=近 28 天；长视频=最新 30 条） | 跨范围不可比；登记项必须写清 `window` 与 `sample_rule` |
| 3 | 长视频样本只有 **4 条** | 必须设样本门槛，低于门槛不出结论 |

### 1.3 口径登记：每个指标登记两个口径

```yaml
id: metric.creator.avg_views_long
label: 长视频均播
axes:
  content_form: long          # long | short | all
surfaces:
  reported:                   # 工具直接返回的那个数
    kind: mean
    window: latest_30_videos
    sample_rule: 最新 30 条里的长视频
    source: 频道档案·表现
    min_sample: 5             # 低于 5 条不出结论
    data_status: unstable_when_small_sample
  median:                     # 自算中位数
    kind: median
    window: last_28_days
    sample_rule: 近 28 天视频里时长 > 60 秒的
    source: 近期视频列表逐条计算
    min_sample: 5
    data_status: reliable_when_sample_ok
external_only: median         # 对外唯一口径（见 §1.5）
owner: 业务-红人组
version: 1.0.0
```

**要点**：不是"一个指标一个数"，而是**一个指标、多个口径、每个口径带窗口与样本规则**。对外只允许引用 `external_only` 指定的那个。

### 1.4 样本门槛（硬规则）

| 样本量 | 处置 |
|---|---|
| ≥ 10 | 正常出结论 |
| 5–9 | 出结论，但交付里必须标"样本 n=6，仅供参考" |
| < 5 | **不出结论**，写"样本不足（n=4），无法判断" |

按实测：Cas and Chary 的长视频只有 4 条 → 若阈值卡"长视频均播 ≥ 50 万"，它会被判为不达标，但这其实**是样本不足，不是表现差**。这个区别必须在交付里说清。

### 1.5 对外唯一口径

- 长／短视频：对外用 **中位数（近 28 天）**；工具返回的均值仅内部参考。
- 若用户要求"就用工具里那个数"，交付必须标注"内部口径，不可对外"。

### 1.6 数值解析规则（否则阈值比较会错）

实测返回的数值格式不统一：

| 字段 | 实测样例 |
|---|---|
| 播放量 | `"1.5 万"`、`3119` |
| 互动率 | `"2.21%"` |
| 订阅数 | `186000` |

解析规则（进登记表 `parsing` 段）：

| 单位 | 换算 |
|---|---|
| `万` | ×10,000 |
| `亿` | ×100,000,000 |
| `k`/`K` | ×1,000 |
| `m`/`M` | ×1,000,000 |
| `%` | ÷100，保留 4 位小数 |

**规则**：比较前必须归一化；解析失败的样本**丢弃并计数**，不能当 0。

## 2. 维度树 + 可得性标记（v1.2 新增）

### 2.1 每条维度多一个字段

```yaml
availability: auto | manual | unavailable
```

| 值 | 含义 | 处理 |
|---|---|---|
| `auto` | 系统里有，可直接取 | 正常问、正常筛 |
| `manual` | 系统里没有，要人工看（如内容形式判断） | 可以问，但交付要写"人工判断" |
| `unavailable` | 取不到（平台未收录） | **不问**，交付里列进"无法评估项" |

### 2.2 实测得到的能力边界

| 维度 | 可得性 | 依据 |
|---|---|---|
| 订阅数、频道属地、总播放、视频数 | `auto` | 频道档案直接给 |
| 长／短视频均播、互动率、平均点赞 | `auto` | 表现块给（注意 §1 的口径限制） |
| 受众性别、年龄分布、地区 Top5、兴趣、购买意向 | `auto` | 受众块给 |
| **频道标签 / 平台 tag** | `unavailable` | 返回里没有 |
| **受众"真实性"（真人/水军）** | `unavailable` | 无此信号，只能靠内容人工看 |
| **内容形式（测评/资讯/对比）** | `manual` | 需看标题与视频 |
| **商业合作史、是否合作竞品** | `manual` | 需查品牌提及模块 |
| **粉丝增长趋势** | `unavailable` | 返回里没有历史快照 |

> 结论：**"受众性别/年龄"能自动取，但"频道标签""粉丝增长"取不到**——v1.1 把这两类混在一起问，会导致"问完发现没有数据"。

### 2.3 树 A：找红人（发现／背调环节）

```yaml
id: criterion.creator.screen
stage: screening
groups:
  - key: content
    label: 内容与垂类
    dims:
      - {key: category,        ask: 垂类范围？智能眼镜 / AR / 可穿戴 / 其他, availability: manual}
      - {key: content_form,    ask: 内容形式？真机上手测评 / 资讯 / 对比 / 开箱, availability: manual}
      - {key: language,        ask: 语言？默认英文, availability: manual}
  - key: audience
    label: 受众与地域
    dims:
      - {key: market_country,  ask: 主要市场国家或地区？, availability: auto, note: 用受众地区占比判，不是频道属地}
      - {key: audience_gender, ask: 受众性别有要求吗？, availability: auto}
      - {key: audience_age,    ask: 受众年龄段有要求吗？, availability: auto}
      - {key: audience_interest, ask: 兴趣人群要与产品相关吗？, availability: auto}
  - key: performance
    label: 表现与规模
    dims:
      - {key: subscribers,     ask: 粉丝量档位？, availability: auto}
      - {key: avg_views_long,  ask: 长视频均播下限？, availability: auto, sampling: min5}
      - {key: avg_views_short, ask: 短视频均播下限？, availability: auto, sampling: min5}
      - {key: engagement_rate, ask: 互动率下限？, availability: auto}
      - {key: upload_frequency, ask: 更新频率要求？（近 90 天发几条）, availability: auto}
  - key: commercial
    label: 商业与合作
    dims:
      - {key: past_similar,    ask: 要求有同类产品合作经验吗？, availability: manual}
      - {key: competitor_conflict, ask: 正在合作竞品的要排除吗？, availability: manual}
  - key: exclusions
    label: 排除项
    dims:
      - {key: already_worked,  ask: 已合作过的要排除吗？默认排除, availability: auto}
      - {key: aggregator,      ask: 纯搬运／资讯号要排除吗？默认排除, availability: manual}
```

### 2.4 树 B：背调（深度评估环节）

```yaml
id: criterion.creator.due_diligence
stage: screening
groups:
  - key: authenticity
    label: 真实性
    dims:
      - {key: views_per_sub,   ask: 播放/粉丝比低于多少算异常？, availability: auto}
      - {key: like_view_ratio, ask: 点赞播放比低于多少算异常？, availability: auto}
      - {key: comment_activity, ask: 评论活跃度要看吗？, availability: unavailable}
      - {key: content_original, ask: 是否排除搬运/无原创？, availability: manual}
  - key: stability
    label: 表现稳定性
    dims:
      - {key: sample_size,     ask: 样本门槛用几条？（默认 5）, availability: auto}
      - {key: view_variance,   ask: 单条播放波动大要不要降级？, availability: auto}
  - key: fit
    label: 匹配度
    dims:
      - {key: category_depth,  ask: 垂类专注度要求？（历史视频里同类占比）, availability: manual}
      - {key: product_affinity, ask: 购买意向与产品相关度要求？, availability: auto}
```

### 2.5 树 C：报价（报价审核环节）

```yaml
id: criterion.creator.quote_review
stage: negotiation
groups:
  - key: quote
    label: 报价本身
    dims:
      - {key: quote_amount,    ask: 对方报多少？货币与含税与否, availability: manual}
      - {key: deliverable,     ask: 交付物是什么？（长视频/Shorts/组合）, availability: manual}
      - {key: usage_rights,    ask: 授权范围？（是否含二次投放）, availability: manual}
  - key: benchmark
    label: 价格合理性
    dims:
      - {key: cpm,             ask: CPM 上限？, availability: auto, formula: 报价 / 播放 × 1000}
      - {key: play_basis,      ask: 用哪个播放口径算 CPM？（长期待定项）, availability: auto}
      - {key: tier_position,   ask: 价格在同量级里的位置？, availability: auto}
  - key: terms
    label: 条款
    dims:
      - {key: payment_terms,   ask: 付款条件？, availability: manual}
      - {key: revision_limit,  ask: 改稿次数上限？, availability: manual}
```

> 报价树的 `cpm` 必须绑定 `play_basis`——用均值还是中位数、用长视频还是整体，CPM 会差好几倍。这是必须显式让用户定的（或按登记表默认值，但交付要写明）。

### 2.6 未筛维度必须显式

交付固定两行：

```
本次筛选维度：内容形式、市场国家、订阅数、长视频均播
本次未筛维度：受众性别/年龄、短视频均播、互动率、更新频率、商业合作
```

第二行不是"不满足"，是"没查"。门禁 C19-f 强制。

## 3. 交互：一次给全 + 按回答动态追问

**不是固定三轮。** 固定轮次会让已经一句话说全的用户被白问两遍——体验差，而且显得笨。

### 3.1 起手：一次把选择面摊开

第一次回复就给全：**维度组 + 每组 2–3 个示例指标 + 默认值**，并明确告诉用户可以一次说完，也可以只说重点。

```
Agent：找红人一般从这五类里筛（括号里是默认值，可直接说「按默认」）：
  ① 内容与垂类（真机上手测评 / 英文）
  ② 受众与地域（美国为主）
  ③ 表现与规模（长视频均播 ≥ 50 万；互动率 ≥ 5%）
  ④ 商业与合作（同类产品经验优先）
  ⑤ 排除项（已合作过、纯搬运号，默认排除）

可以一句话说全（例：「美国、长视频 30 万、排除已合作」），也可以只说重点，其余按默认。
```

### 3.2 追问规则：按「覆盖度」决定问几轮

收到回答后先解析覆盖度，再决定要不要追问——不按预设轮次走。

| 情况 | 处理 | 例子 |
|---|---|---|
| **一次说全**（关键维度都有值） | **0 追问**，复述一遍确认即开工 | 「美国、长视频 30 万、排除已合作」→ 直接确认 |
| **给了方向但没给阈值** | 只追问缺的阈值（1 轮，最多 2–3 项） | 「找测评博主」→ 问「长视频均播和互动率按默认吗？」 |
| **只给了模糊方向** | 追问 1 轮方向，再按选择展开 | 「找点科技博主」→ 问「内容形式要测评还是也收资讯？」 |
| **答得自相矛盾／偏题** | 指出矛盾点，问一次澄清 | 「只要短视频」但阈值填了「长视频均播 30 万」 |
| **连续 2 轮仍不明确** | 按默认值跑，交付显式标「未确认项」 | 不再追问，避免变成问卷 |

**追问上限**：默认 2 轮（可配）。到上限不再问，改用默认值并在交付里写明——**宁可标「未确认」，也不把用户拖进第三轮问答**。

### 3.3 缺口排序：先问影响最大的

不是「缺什么问什么」，而是按 **影响大小 × 是否必需** 排序，只问前 2–3 个：

| 权重 | 判据类型 | 例子 |
|---|---|---|
| 高 | `resolution: required` | 预算档位、合作形式（答不出做不了） |
| 高 | 直接决定名单构成的 | 内容形式（测评／资讯）、排除项 |
| 中 | 表现阈值 | 长视频均播、互动率 |
| 低 | `default_ok` | 时间窗、是否含历史已合作 |

规则：`availability: unavailable` 的维度**从不出现**在提问里；`manual` 的会问，但交付要标「人工判断」。

### 3.4 兜底一：用户不知道定多少 → 给分布参考



不能干问"下限多少"。用户答不上来时，给同类分布作参考：

```
Agent：要不要先看同类红人的分布再定？
  最近检索到的同垂类 60 个频道：长视频均播 P50 ≈ 1.8 万，P90 ≈ 12 万
  你要卡在 P50、P75 还是别的？
```

分布来源：候选检索结果的中位播放字段（真实检索结果，不是估的）。

### 3.5 兜底二：一句话直连

用户直接说全了 → 没有任何追问，只复述确认一次：

```
Agent：按你刚才说的，本次筛：市场美国 / 长视频均播 ≥ 30 万 / 排除已合作
  其余不筛：受众、短视频、互动率、更新频率、商业合作
  这样对吗？确认就开工。
```

### 3.6 兜底三：`task_context` 落点与生命周期

| 项 | 设计 |
|---|---|
| 落点 | 本机文件 `$DANIEL_HOME/task-context/<任务指纹>.json`（不进包、不进交付物） |
| 任务指纹 | `品牌 + 需求摘要哈希`，同一需求二次追问命中同一份 |
| 有效期 | 24 小时；过期视为新任务，重新确认 |
| 内容 | 选中的维度、取值、未筛清单、确认时间、默认值版本 |
| 中断续跑 | 用户隔一会儿回来说"继续"，按指纹找回；指纹对不上就重新确认 |
| 交付引用 | 交付物页脚落"本次口径确认时间 + 取值摘要" |

## 8. 治理（v1.2 新增）

| 项 | 规则 |
|---|---|
| **新维度沉淀** | 用户在任务中提出的新维度记入 `task_context`；同一维度被提 **3 次** → 列为候选 → 业务评审 → 进母本 |
| **默认值变更** | 改默认值 = 改母本 → 升 `corpus_version` → 变更日志写明"旧值→新值 + 原因"；交付标注默认值版本 |
| **不可比提示** | 默认值变更前后的交付结果不可直接对比，交付说明里要提示 |
| **与错题集的关系** | 现有 KOL 错题集（`docs/marketing/kol/2026-09-13-*.xlsx`）是判据来源之一，登记项引用它，不另立一套 |
| **文档一致性** | v1.0/v1.1 归档；产品文档 §5 的访谈反馈（模糊需求要追问）由本方案的 §3 承接，需在产品文档里回链 |

---

## 9. 风险与不做

| 风险 | 处置 |
|---|---|
| 指标口径再变（如工具改算法） | 登记项带 `surfaces`，变更走版本 |
| 追问过多让用户烦 | **按覆盖度动态追问，一轮说清就 0 追问**；上限 2 轮，超限按默认并标「未确认」 |
| 人工判断维度不可校验 | 交付标"人工判断"，不进自动门禁 |
| 判断质量本身 | 机器只能保证判据统一、口径可查、结构一致；质量靠复盘 |

**不做**：数据仓库、指标计算引擎、权限系统、自动改写业务定义、新工具、新能力束、新 MCP 服务。
