# Daniel Bot 语义层（Ontology）设计方案 v0.3

> **v0.3 变更（两处关键修正）**
> 1. **形态**：不再作为独立 MCP server，而是**包内资产**——与 `mcp/corpus`（能力／工序语料）、`contracts`（交付与读链契约）并列，随包发布、随包版本化。
> 2. **不另造机制**：包内已有交付契约（`contracts/*.json` 含输入／前置／步骤／自检／判据出处）与读链信封（`daniel.read.v1`）。语义层**扩展**它们，不并行造第二套。
>
> 状态：待评审，不含排期。
> 关联：`01-目的优化提案与需求示例清单.md`、`02-填充稿-综合场景需求示例.md`、产品文档 §4.1 当前卡点。

---

## 0. 一句话

> Daniel Bot 现在**只有上限、没有下限**：模型强一点就好，弱一点就散。语义层要把「怎么定义、怎么算、怎么走、怎么说」从模型自由发挥里收回来，**让最弱的模型也能达到可交付的下限**——而它是包内的一个部件，不是 Daniel 对外新开的一个服务。

---

## 1. 包内四个并列资产（这就是"层"的落地形态）

```
vendor/data/daniel-cli/
├── mcp/
│   ├── server.py            MCP 接口层（89 个工具的实现）
│   └── corpus/              能力层 · 工序层（8 束语料，24 切片，40 文件）
├── contracts/               契约层（已有）
│   ├── read-envelope.md     读链结构化输出契约（daniel.read.v1）
│   └── high-performance-video-list.json   交付契约（输入/前置/步骤/自检/判据出处）
├── ontology/                ← 新增 · 语义层
│   ├── concepts/            业务概念（红人、垂类、报价、火爆…）
│   ├── metrics/             指标口径（含 data_status 可靠性）
│   ├── logic/               推理契约（步骤 + 卡点 + 必填证据）
│   └── index.json           构建产物：只读索引（几十 KB，随包分发）
└── daniel_cli/              命令实现
```

**关系一句话**：`corpus` 是给人读的判据与工序（散文），`ontology` 是给机器查的定义与约束（结构化），`contracts` 是把两者落到一次交付上的执行契约。

三者不重复：**散文讲为什么，索引讲是什么，契约讲怎么跑与怎么验。**

---

## 2. 要统一的是三件事

| 层 | 统一什么 | 靠什么 | 现有资产 |
|---|---|---|---|
| **结果一致** | 概念定义、指标口径、数字来源 | `ontology/metrics` + `data_status` | 新增 |
| **过程一致** | 执行步骤、判断顺序、何时停下来问人 | `ontology/logic` + 契约的「前置／步骤」 | **部分已有**（交付契约已写步骤与自检） |
| **表达一致** | 交付结构、说话风格、禁用表述 | `ontology/output` + 契约的 schema | **部分散落在 corpus**，需抽出来 |

只做第一件，产品仍不稳：口径对了，但有的只给结论不给证据、有的把“可能”说成“确定”。

---

## 3. 三层约束怎么落地

### 3.1 结果一致：Metric 带可靠性

```yaml
id: metric.creator.avg_views_28d
label: 均播（近 28 天）
definition: 近 28 天发布视频播放量的中位数（非算术平均）
formula: median(views where published_at >= today-28d)
data_status: unreliable        # reliable | unreliable | unknown ← 把"均播不准"写进模型
status_reason: 当前 MCP 返回均播与实际有偏差，聚合值需回源核对
fallback: 用 videos[].views 自行计算中位数
owner: 业务-红人组
version: 1.2.0
```

`data_status` 是这一层最有价值的设计：把“字段不准”从口口相传变成可查询事实；agent 引用时必须带标注。

### 3.2 过程一致：逻辑契约复用现有「步骤」结构

现有交付契约里已经有 `前置 / 步骤 / 自检`。语义层不另造，而是**把可复用的判断顺序抽到 `ontology/logic/`**，让多个交付契约引用同一份：

```yaml
id: logic.screen_kol
steps:
  - id: s1_parse
    required: 明确对象、市场、预算档位、时间要求；缺项必须先追问
    gate: ask_before_proceed          # 卡点写进契约，不靠模型自觉
  - id: s2_criteria
    required: 筛选条件翻译成可计算指标（引用 metric id），不许用形容词
  - id: s3_search
    required: 检索式矩阵 ≥3 组，注明预期命中
    gate: show_before_execute
  - id: s4_screen
    required: 逐条给排除理由（引用 constraint id）
forbidden: [跳过 s2 直接检索, 用"感觉很合适"作为唯一理由]
```

### 3.3 表达一致：输出契约从 corpus 抽出来

现在交付的长相写在 corpus 散文里（“结论先行”“每条带原话”）。抽成结构：

```yaml
id: output.kol_list
sections: [概览, 名单, 每条依据, 覆盖率与缺口, 下一步]
tone: [结论先行, 数字必须带口径与时间点, 不确定写待确认]
banned: [非常好, 绝对, 肯定没问题, 大概]
required_trace: [s1_parse, s2_criteria, s3_search, s4_screen]
```

`banned` 不是文风洁癖——**含糊词是把“没判断”伪装成“判断”**，也是跨 agent 分歧的最大来源。

## 4. 强制力：复用包内已有的"契约自检"机制

包内交付契约本来就有「自检」段（五条，跑成可复算回归）。语义层把这件事统一成一个入口：

| 机制 | 做法 | 复用度 |
|---|---|---|
| **① 开工前置** | `describe_task(task_type)` 返回三份契约（结果／过程／表达） | 新增工具，数据来自 `ontology/` |
| **② 交付前校验** | `validate_deliverable(草稿, task_type)`：跑输出契约的段检查 + 禁用词 + 步骤痕迹是否齐全 | **复用契约自检的思路，扩成通用** |
| **③ 不过就返工** | 自己改 → 再校验（≤N 轮）→ 仍不过如实标"未达标项" | 新增 |
| **④ 版本留痕** | 交付物落 `ontology_version` + `contract_version`（契约已有版本号） | 半复用 |

**因为都在包内，硬门成本很低**：插件自己的工具在本地就能判「有没有读过契约、有没有跑校验」，不需要跨进程票据。P0 就可以把「未校验不得交付」做成默认行为。

---

## 5. 一致性怎么度量

固定 20 个任务集（检索／背调／报价／名单／报告 五类），在强／中／弱三个模型上跑：

| 指标 | 目标 |
|---|---|
| 数字一致率（关键数字跨模型一致） | ≥ 95% |
| 步骤完整率（契约步骤走完） | ≥ 95% |
| 结构合规率（必需段齐全） | 100% |
| 禁用词命中率 | ≤ 5% |

**验收线不是“强模型多好”，而是“强弱差距”**：

> 现状预估 强 90 / 弱 50（差 40）→ 目标 强 90 / 弱 75（差 15）。
> 上限不必压，**下限必须抬**。这就是「模型无关性」。

## 6. 融合：包内三处改动，不碰接口层

| 接触点 | 改什么 | 不改什么 |
|---|---|---|
| `mcp/corpus` | 正文里的具体阈值与步骤顺序**迁到 ontology**，正文只留判据理由与话术 | 语料结构与话术 |
| `contracts/*.json` | 「判据出处」从"章节+行号"升级为"章节+行号 ＋ metric id"；引用 `logic.*` 而非内联步骤 | 契约既有字段与自检结构 |
| 插件内置工具 / CLI | 增加 `describe_task` / `validate_deliverable`；`--json` 数值字段带 `metric_id` + `data_status` | 现有工具与命令 |

**关键原则：接口层（MCP 89 工具）不动**——语义层是它上面的一层解释与校验，不是它的替代。

## 7. 维护与迭代（防腐化）

| 机制 | 做法 |
|---|---|
| 源文件 | git 里的 YAML，一对象一文件；构建产出 `index.json` 随包 |
| 责任 | 每个 metric / contract 必须有业务 owner；无 owner 不上线 |
| 变更 | PR + owner 审批 + 语义版本（改定义 = major）；版本随包号发布 |
| 防双写 | CI 双向检查：corpus 正文不许出现具体阈值；ontology 对象必须被至少一个契约或语料引用 |
| 漂移检测 | ① 20 任务 × 3 模型一致性测试进 CI；② `data_status=unreliable` 字段每周抽样回源 |
| 废弃 | deprecated → 双跑 2 周 → 移除 |

## 8. 分阶段

| 阶段 | 范围 | 交付 |
|---|---|---|
| **P0（2–3 周量级）** | 10 个高频指标 + 5 个概念 + 2 份契约（`logic.screen_kol`、`output.kol_list`）+ `validate_deliverable` 进插件 + 20 任务基线 | 跑通"一个任务、三个模型、结果可对比" |
| **P1** | 补齐报价／背调／报告三类契约；`data_status` 覆盖全部数值字段；一致性测试进 CI | 覆盖主要交付物 |
| **P2** | 自进化（从交付中沉淀新概念，人工审核后入库，参考 EvoOntology） | 闭环 |

**P0 选 `screen_kol` 的理由**：最高频、跨模块步骤最多、最容易暴露模型差异——用它验证"弱模型能否被拉到下限"最有说服力。

---

## 9. 验收标准

| # | 判据 | 测法 |
|---|---|---|
| 1 | 弱模型达到下限 | 20 任务 × 弱模型：结构 100%、步骤 ≥95%、数字 ≥95% |
| 2 | 强弱差距收敛 | 综合分差距 ≤15（现状预估 40） |
| 3 | 可追溯 | 任取一份交付，能查到 `ontology_version` + `contract_version` + 每个指标的 `data_status` |
| 4 | 无绕过 | 未跑校验的交付 ≤1/20（P0 软门期的现实目标） |

## 10. 风险与「不做什么」

| 风险 | 处置 |
|---|---|
| 契约写太细，把 agent 变成机器人 | 只约束结论、步骤、结构、语气；措辞自由 |
| 校验走过场 | 校验项必须能对应内容（如"每条依据引用 constraint id"），不接受空话 |
| 与 corpus 双写 | CI 双向检查（见 §7） |
| 抬下限压掉上限 | 只"不达标打回"，不"超出打回" |
| 包体变大 | 索引是纯文本 JSON，几十 KB 级；构建期生成，不引入运行时依赖 |

**明确不做**：不做数据仓库、不做指标计算引擎（计算仍在接口层）、不做权限系统、不自动改写业务定义。
