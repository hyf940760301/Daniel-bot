# Daniel Bot 语义层（Ontology）设计方案 v0.1

> 定位：**地基级方案，不是功能**。目标是在不改动现有四层（MCP / Agent / Skill / 插件）的前提下，往中间插一层「可查询、可强制、可版本化」的业务语义层。
>
> 状态：待评审。本文只谈设计，不含实施排期。
> 关联：`01-目的优化提案与需求示例清单.md`、`02-填充稿-综合场景需求示例.md`、产品文档 §4.1 当前卡点。

---

## 0. 一句话

> 把「营销业务怎么定义概念、怎么算指标、什么不能做」从**散落在 skill 提示词里的自然语言**，变成**结构化、可查询、带版本与责任人的注册表**；agent 干活前先查它，交付时带上用的是哪一版。

---

## 1. 它凭什么算"层"，而不是"一份文档"

判据只有三条，缺一条就不算层：

| # | 判据 | 反例（现状） |
|---|---|---|
| 1 | **可查询** | 口径写在 skill 正文里，模型只能"读到"，不能按 id 精确取用 |
| 2 | **可强制** | "必须先读"只是提示词，模型可以直接调 MCP 拿数绕过 |
| 3 | **可版本化** | 口径改了没人知道哪份报告用的是旧定义 |

一句话分工：**skill 管「怎么干」，语义层管「概念和数字怎么定义」**。skill 里不再写死口径，只引用 id。

---

## 2. 现状约束（设计必须兼容的真实条件）

| 面 | 现状 | 对设计的约束 |
|---|---|---|
| MCP | 89 个工具，stdio 常驻 | 语义层不能要求 MCP 大改，只能**加返回值字段**或**加一层前置校验** |
| CLI | 89 条命令 / 22 模块 | 与 MCP 共用同一套输出契约，字段签名要一致 |
| 插件 | 12 个内置工具 + 随包 skill | 插件是主推形态，**内置工具是最容易加强制的地方** |
| Skill | 8 束 / 24 切片 / 40 文件 / 语料 0.9.204 | 存量口径全在正文里，只能**渐进迁移**，不能一次性重写 |
| 已知卡点 | MCP 不稳、字段（均播）不准、授权未自动化 | 语义层要能**显式标注字段可靠性**，否则会把脏数据放大成结论 |

**结论：语义层必须是"叠加上去"的一层，不能要求先重构现有四层。**

---

## 3. 物理形态选型

| 方案 | 形态 | 可版本化 | 可强制 | 改造量 | 建议 |
|---|---|---|---|---|---|
| **A. 独立 MCP server（推荐）** | 新的 `daniel-ontology` server，4–6 个只读工具 | ✅ 独立发版 | ✅ 自己是唯一入口，可在数据侧校验 | 新增一个包，现有不改 | **P0 采用** |
| B. 与现有 MCP 合体 | 同一 server 多一个 namespace | ⚠️ 跟数据接口绑版本 | ✅ | 小 | P1 可选（减少一次连接） |
| C. 文件 + skill 读取 | 仓库里的 yaml，agent 自己读 | ⚠️ 靠 git tag | ❌ 无强制力 | 最小 | 只作为 A 的**源文件形态** |

**选 A + C 组合**：源文件是 git 里的 YAML（人可评审、可 diff），构建成只读索引，由独立 MCP server 暴露查询工具。这样改口径是提 PR，不是改代码逻辑。

## 4. 数据模型（五类对象）

| 类型 | 是什么 | 关键字段 |
|---|---|---|
| **Concept** | 业务概念（红人、垂类、合作、报价、火爆） | id / 定义 / 同义词 / 上位概念 |
| **Metric** | 可计算指标 = 口径 + 算法 + 依赖 + **可靠性** | id / formula / deps / unit / reliability / owner / version |
| **Relation** | 对象之间关系（红人—合作—报价；红人—垂类） | from / type / to / 基数 |
| **Constraint** | 行为约束（写前置、权限、禁用表述） | id / 作用域 / 触发条件 / 处置 |
| **Evidence** | 口径的证据（样例、抽查记录、来源链接） | id / 指向对象 / 样本量 / 结论 |

### 4.1 Metric 的写法（直接编码"均播不准"这个卡点）

```yaml
id: metric.creator.avg_views_28d
type: metric
label: 均播（近 28 天）
definition: 近 28 天发布视频的播放量中位数（不是算术平均）
formula: median(views where published_at >= today-28d)
unit: 次
deps:
  - mcp: creator.profile
  - field: videos[].views
data_status: unreliable          # reliable | unreliable | unknown  ← 关键
status_reason: 当前 MCP 返回的均播与实际存在偏差，聚合值需回源核对
fallback: 用 videos[].views 自行计算中位数
owner: 业务-红人组
version: 1.2.0
updated: 2026-10-29
evidence: [evidence.avg_views.2026-10.spotcheck]
```

**`data_status` 是这一层最有价值的设计**：它让"字段不准"这件事从口口相传变成可查询的事实。agent 引用该指标时，交付里必须带"该口径当前不可靠"的标注，而不是直接拿去汇报。

### 4.2 Concept 的写法（解决"火爆"这类模糊词）

```yaml
id: concept.creator.hot
type: concept
label: 火爆（红人）
definition: 以下三条同时满足
criteria:
  - metric: metric.creator.follower_growth_30d
    op: ">"
    value: 0.20
  - metric: metric.creator.avg_views_7d
    op: ">"
    value: 500000
  - metric: metric.creator.engagement_rate
    op: ">"
    value: 0.05
threshold_owner: 业务-红人组        # 阈值必须业务定，工程不代拟
version: 0.1.0
status: draft                      # draft 的口径不得用于对外交付
```

两个硬规矩：**阈值由业务签**；**draft 状态的口径不允许进交付物**。

## 5. 查询接口（工具面，只读）

| 工具 | 入参 | 出参 | 用途 |
|---|---|---|---|
| `describe_domain` | 领域（如 creator/outreach/sov） | 该领域的对象清单 + 版本 | **开工第一步** |
| `search_objects` | 关键词 | 命中的 concept/metric | 模糊词落位 |
| `get_object` | id | 完整定义（含 data_status） | 精确取口径 |
| `traverse` | id + 关系类型 | 关联对象 | 找依赖字段、找上下游 |
| `validate_claim` | 一个陈述（如"该红人很火爆"） | 能否被现有口径支撑 + 缺什么 | **交付前自查** |

每次返回都带 `ontology_version`（如 `2026.10.29-3`），便于事后追溯。

## 6. 怎么融合——五个接触点，逐个说改什么

| # | 接触点 | 改什么 | 不改什么 |
|---|---|---|---|
| 1 | **Skill** | frontmatter 增加 `ontology: [metric.*, concept.*]`；正文里的具体阈值/口径改成引用 id；CI 校验被引用对象存在且非 `draft`/`deprecated` | skill 的结构、话术、工序顺序全部不动 |
| 2 | **MCP 返回值** | 数值字段附带 `metric_id` + `ontology_version` + `data_status`（加字段，不改结构） | 工具名、入参、既有字段 |
| 3 | **插件内置工具** | 开工前调一次 `describe_domain`；交付前调 `validate_claim` | 12 个工具的行为 |
| 4 | **CLI** | `--json` 输出同一套字段签名 | 命令与参数 |
| 5 | **交付物** | 报告页脚 / 表格说明页落 `ontology_version`；`data_status=unreliable` 的指标自动加注 | 排版 |

**融合的关键是第 1 条**：skill 从"口径的持有者"退化为"口径的使用者"。这一步做完，语义层才算真的接上了。

## 7. 强制力：先软门，后硬门

「agent 必须先读」必须有机制兜底，否则等于没写。

| 阶段 | 机制 | 成本 | 拦截效果 |
|---|---|---|---|
| **P0 软门** | 数据 MCP 返回值带 `metric_id` + `data_status`；交付物落 `ontology_version`；抽检交付是否带标注 | 低（只加字段） | 能事后发现绕过，不能事前阻断 |
| **P1 硬门（ticket）** | `describe_domain` 换取短时票据（如 5 分钟、绑定领域），数据 MCP 校验票据，无票拒绝聚合类字段 | 中（两个 server 耦合） | 事前阻断 |
| **不建议 P0 就做硬门** | 会把两个 server 的可用性绑死——MCP 本身已不稳，再加一层校验会放大故障面 | — | — |

**建议：P0 用软门把数据留痕做起来，等 MCP 稳定性问题解决后再上硬门。**

## 8. 维护与迭代（这一层最容易死在这里）

| 机制 | 做法 |
|---|---|
| **源文件** | git 里的 YAML，一对象一文件（`concepts/` `metrics/` `constraints/`），review 即评审 |
| **构建** | CI 构建只读索引（json/sqlite），随 MCP server 发布；索引可热更新，不必重启 |
| **变更流** | PR → 对应 `owner` 审批 → 版本号（major 改定义 / minor 加字段 / patch 修文案）→ 合并即生效 |
| **责任人** | 每个 metric 必须有业务 owner（不是工程代管）；无 owner 的对象**不允许上线** |
| **漂移检测** | ① 一致性测试：同 20 个问题跑 3 个模型，关键数字一致率 < 95% 报警；② 数值抽查：`data_status=unreliable` 的字段每周抽样回源比对 |
| **废弃** | `deprecated` → 双跑 2 周（新旧口径同时算，差异超阈值告警）→ 移除 |
| **腐化防线** | CI 检查：skill 引用的 metric 必须存在、非 draft、非 deprecated；skill 正文里**不许再出现具体阈值数字**（出现即报错，防止双写） |

## 9. 分阶段

| 阶段 | 范围 | 交付 | 时间感 |
|---|---|---|---|
| **P0** | 5 个核心概念 + 10 个高频指标（pitch 人数、送达、已读、回复率、均播、互动率、订阅数、视频数、SOV 提及数、报价金额）；只读 MCP；软门 | 语义层 server + 索引 + skill 引用改造（先改 2 个 skill 试水）+ CI 校验 | 2–3 周量级 |
| **P1** | 关系层（红人—合作—报价、红人—垂类）＋ 约束层（写前置检查）＋ 一致性测试进 CI | 关系查询 + 约束校验 | 视 P0 效果 |
| **P2** | 硬门 ticket；自进化（交付中沉淀的新概念，人工审核后入库，参考 EvoOntology 的 attribution-guided edits） | 闭环 | 后续 |

**P0 的选取原则：只做日报/周报实际在用的口径**——先证明它在真实交付里有用，再扩全域。全域本体是典型的"做三年没人用"。

## 10. 验收标准（可测，不是感觉）

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | **口径一致** | 同一问题交给 3 个不同模型/agent，关键数字一致率 ≥ 95% |
| 2 | **可追溯** | 任取一份交付物，能查到它用的 `ontology_version` 与每个指标的 `data_status` |
| 3 | **不腐化** | CI 能拦住「skill 引用不存在的指标」和「skill 正文里写死阈值」两类提交 |
| 4 | **无强制绕过** | 抽检 20 次交付，未带 `ontology_version` 的 ≤ 1 次（软门阶段的现实目标） |

---

## 11. 风险与「不做什么」

| 风险 | 处置 |
|---|---|
| 双写（skill 里又写一遍口径） | CI 禁止阈值出现在 skill 正文 |
| 过度建模（建了几百个概念没人用） | 只做被引用的；未被引用 90 天自动标 `unused` |
| 语义层成为瓶颈（改口径要等发版） | 索引热更新，YAML 合并即生效 |
| 字段本身不准，口径再准也没用 | `data_status` 显式标注 + 交付加注（不假装解决） |

**明确不做**：不做数据仓库、不做指标计算引擎（计算仍在 MCP 侧）、不做权限系统（权限仍在业务系统）、不做自动改写业务定义（自进化只到"提议"）。
