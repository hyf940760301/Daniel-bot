# 方案审查清单（方案代理 / 审查代理 共用）

> 由来：2026-10-29 语义层方案 v0.1–v0.3 连续出现「把包内资产设计成对外 MCP server」等根本性错误，用户要求改为「一个出方案 + 一个审方案」的双代理机制。本清单是审查代理的判据，也是方案代理的自检表。
>
> 判定原则：**审查代理独立核对事实，不采信方案里的自我陈述。**

---

## A. 事实类（每条必须能落到文件）

| # | 检查项 | 打回条件 |
|---|---|---|
| A1 | **现状资产盘点表**是否先于方案出现 | 没有这张表 → 直接打回，不进入后续审查 |
| A2 | 盘点表里的每个资产是否真实存在 | 路径不存在 / 名称对不上 → 打回 |
| A3 | 方案里每个"新增"是否标了「已有等价物：无 / 有，在 X」 | 缺标 → 打回 |
| A4 | 标"有"的地方，是否写成了"新建"而不是"扩展/复用" | 是 → 打回（这是 v0.3 的核心错误类型） |
| A5 | 数字类事实（工具个数、语料版本、文件行数、模块数）是否与文件一致 | 抽查 3 处不一致 → 打回 |
| A6 | 所有无文件依据的陈述是否标了 `【待验证】` | 未标且属事实判断 → 打回 |

## B. 逻辑类

| # | 检查项 | 打回条件 |
|---|---|---|
| B1 | 形态决策是否写明「来源」：需求推出 / 参考资料类比 | 没写 → 打回 |
| B2 | 若来源是类比，是否说明了为什么适配我们的分发方式 | 没说明 → 打回 |
| B3 | 新增组件是否引入了已知不稳定面（如再加一个常驻进程/网络路径） | 引入且未论证 → 打回 |
| B4 | 「扩展既有机制」的落点是否具体到文件与字段 | 只说"扩展现有契约" → 打回 |

## C. 可执行类

| # | 检查项 | 打回条件 |
|---|---|---|
| C1 | 分阶段（P0/P1/P2）是否有可交付物与验收判据 | 缺 → 打回 |
| C2 | P0 是否最小可用（只做被引用的，不做全域） | 铺全量 → 打回 |
| C3 | 每条约束是否有执行机制（不是"应当""必须"这种口号） | 只有口号 → 打回 |
| C4 | 度量是否可测（有数字、有对比组、有目标值） | 无法测 → 打回 |

## D. 一致性类

| # | 检查项 | 打回条件 |
|---|---|---|
| D1 | 与上一版相比，改动点是否列清（版本变更说明） | 缺 → 打回 |
| D2 | 是否与既有文档口径冲突（产品文档 4.1 卡点、包内契约版本） | 冲突未说明 → 打回 |
| D3 | 是否出现"另开一套源"（同一个东西两个维护入口） | 出现 → 打回 |

---

## E. 审查代理的输出格式

```
判定：PASS / FAIL
打回项：
  - [A4] <具体问题> —— 证据：<路径:行/字段> —— 修法建议：<一句话>
  - ...
通过项：<只在 PASS 时列>
```

**规则**：
- FAIL 必须给出「问题 + 证据 + 修法」三件套，不许只写"感觉不对"；
- 审查代理**不得**直接改方案文件，只出缺陷；
- 方案代理改完后，**审查代理重新独立核对**，不继承上一轮的"看起来没问题"。

## F. 本次已犯过的错误（重点盯这几类）

1. **照抄参考实现的形态**（EvoOntology 是 MCP server → 我们也做 server），没回到"我们的产品怎么分发"。
2. **没盘点现状就设计**（包内已有 corpus / contracts / 生成管线 / clarify，一个都没看）。
3. **数字记错**（14 个工具写成 12 个）。
4. **把已有机制当新设计**（`daniel_clarify` 已存在，`ask_before_proceed` 是重复发明）。
5. **另开维护源**（语料从母本切出，方案却主张手写 YAML 一对象一文件）。
