## 0. 最重要的变更：判据不是"标准"，是"问法"

v1.0 把阈值写死在登记项里（`火爆 = 增幅>20% 且 均播>50万 且 互动率>5%`），这等于**工程替业务拍标准**。按 Q3 的裁决，改成：

> **登记项只负责"该问什么、为什么问、不答会怎样、默认给个参考"；最终取值由用户在任务开始前确认，落成 `task_context`，交付时写明本次用的是哪组值。**

这是一处结构性改动，影响三节（§2.2、§5 流程、§8 门禁）。

## 1. 判据登记：分层维度模型

### 1.1 为什么要分层

找红人不是"定一两个数"就能开工的：均播还分长短视频，此外还有垂类标签、国家、受众结构、合作史。一次性问固定几条阈值，等于**维度缺失，而且缺了没人知道**。

所以登记项不是"一条判据一个阈值"，而是**一棵维度树**：先给方向（L1），再给细分（L2），最后才问阈值（L3）。用户可以在任何一层补充新维度。

### 1.2 模型

```yaml
id: criterion.creator.screen
type: criterion
label: 找红人 · 筛选维度
stage: screening
selection: user_picks            # 用户选哪些维度，就只筛哪些
unselected: record_explicitly    # 未选的维度必须在交付里列明"本次未筛"

groups:
  - key: content
    label: 内容与垂类
    dims:
      - key: category
        ask: 垂类范围？（智能眼镜 / AR / 可穿戴 / 其他）
      - key: format
        ask: 内容形式？（真机上手测评 / 资讯 / 对比 / 开箱）
      - key: language
        ask: 语言？默认英文

  - key: audience
    label: 受众与地域
    dims:
      - key: country
        ask: 主要市场国家或地区？可多选
      - key: audience_gender
        ask: 受众性别有要求吗？
      - key: audience_age
        ask: 受众年龄段有要求吗？

  - key: performance
    label: 表现与规模
    dims:
      - key: subscribers
        ask: 粉丝量档位？
      - key: avg_views_long
        ask: 长视频均播下限？（近 30 天中位数）
        default: 500000
        resolution: ask_once_per_task
      - key: avg_views_short
        ask: 短视频均播下限？（只看长视频的话这项不筛）
      - key: engagement_rate
        ask: 互动率下限？
        default: 0.05
        resolution: ask_once_per_task
      - key: growth_30d
        ask: 近 30 天增长有要求吗？

  - key: commercial
    label: 商业与合作
    dims:
      - key: past_similar
        ask: 要求有同类产品合作经验吗？
      - key: competitor_conflict
        ask: 正在合作竞品的要排除吗？

  - key: exclusions
    label: 排除项
    dims:
      - key: already_worked
        ask: 已合作过的要排除吗？默认排除
      - key: aggregator
        ask: 纯搬运／资讯号要排除吗？默认排除
```

### 1.3 提问分三轮（递进，不一次问完）

| 轮次 | 做什么 | 用户要回什么 |
|---|---|---|
| **R1 方向** | 列出 5 个方向，每方向给 2–3 个示例指标，**只让用户选方向** | 「内容 + 表现 + 排除项」 |
| **R2 细分** | 对选中的方向展开细分指标，让用户**选具体指标** | 「粉丝量 + 长视频均播，短视频不看」 |
| **R3 阈值** | 只对选中的指标问默认值与是否调整 | 「长视频均播按 30 万」 |

用户在任何一轮都可以说「再加一个 xxx」——登记为本次任务的扩展维度，进 `task_context`，**不立即写进母本**；如果反复出现（比如三个月内多次被提出），P1 再考虑沉淀成正式维度。

### 1.4 实际长什么样

```
用户：帮我找 20 个做智能眼镜测评的红人

Agent（R1 方向）：
  找红人一般从这五类里筛，你先说要不要（也可以补充）：
  ① 内容与垂类  ② 受众与地域  ③ 表现与规模  ④ 商业合作  ⑤ 排除项
  ③ 里比如粉丝量、长视频均播、短视频均播、互动率、增长

用户：①③⑤，重点看长视频，美国市场

Agent（R2 细分）：
  ③ 里要哪几个？粉丝量 / 长视频均播 / 短视频均播 / 互动率 / 增长
  你说重点看长视频——那短视频均播就不筛了，对吗？

用户：对，粉丝量 + 长视频均播

Agent（R3 阈值）：
  长视频均播下限默认 50 万（近 30 天中位数），按 50 万还是改？

用户：按 30 万

→ 本次筛选维度：内容形式、国家、粉丝量、长视频均播
  本次未筛：受众性别/年龄、短视频均播、互动率、增长、商业合作
  取值：长视频均播 30 万（用户确认，默认 50 万）
```

### 1.5 未筛的维度必须显式列出来

交付物固定两行：

```
本次筛选维度：内容形式、国家、粉丝量、长视频均播
本次未筛维度：受众性别/年龄、短视频均播、互动率、增长、商业合作
```

第二行的意思不是"这些不满足"，而是"**这些没查**"。这样维度缺失是显式的、可追溯的——而不是等名单交出去以后，才有人问"你按受众筛了吗"。

### 1.6 `resolution` 是什么：判据的「确认档位」

`resolution` 是**每条细分维度自己的一项设置**，决定这条维度要不要问、能不能用默认值。

| 档位 | 含义 | 例子 |
|---|---|---|
| `required` | **没有默认值，答不出来就不开工** |「这次预算档位是多少？」 |
| `ask_once_per_task` | **有默认值，但每个任务都要问一次**；用户可以说「按默认」 |「长视频均播下限按 50 万，要改吗？」 |
| `default_ok` | **不问，直接用默认**，交付里注明用了默认 |「时间窗默认近 30 天」 |

补充两条规则：

- 分档**只在同一环节内比较**——跨环节的维度根本不会在同一时点被问（见 §1.7）；
- R3 只问 `required` 与 `ask_once_per_task` 的维度，`default_ok` 的直接写在交付说明里。

### 1.7 判据必须分环节（`stage`）

| 维度 | 属于哪个环节 | 什么时候问 |
|---|---|---|
| 垂类、内容形式、国家、受众、表现、排除项 | **发现／背调** | 找红人开工前 |
| **Shorts 还是长视频（作为合作形式）、付费还是置换、预算档位** | **报价审核／合作执行** | 有候选、进入建联时 |

在"找红人"阶段就问合作形式，等于**提前引入一个此阶段用不上的变量**：用户要多答一个与当前决策无关的问题，判断也不会更准。

规则：只有 `stage` 匹配当前环节的维度才会被问；同一概念在不同环节可以是两条独立判据（"接受不接受 Shorts 内容"在背调是内容形式，在报价是合作形式与价格）。

## 2. 流程变化：追问成为必经点

原 v1.0 第 3 步只是"需求模糊时补输入"。现在第 3 步升级为**判据确认**：

| # | 步骤 | 变化 |
|---|---|---|
| 2 | `daniel_skills_list` | 不变 |
| **3** | **`daniel_clarify`（三轮）** | **新增职责**：R1 出方向（维度组）→ R2 展开细分指标供选 → R3 只对选中的指标问阈值。**只问 `stage` 匹配当前环节的**，跨环节一律不问 |
| 3.5 | **写入 `task_context`** | 新增：① 选了哪些维度 ② 各维度取值 ③ **未选的维度清单**（用于交付时显式声明） |
| 4 | `daniel_skills_read` | 展开登记项时，**同时读取 `task_context`**：正文里显示"本次取值"而非"默认值"；未选的维度不展开 |
| 6 | 判断 | 按 `task_context` 的取值判，不按默认值判；未选的维度不做筛选 |
| 8 | 交付校验 | 三条：① `resolution != default_ok` 的维度必须有取值记录 ② 交付必须列出"本次筛选维度 / 本次未筛维度" ③ 未列未筛维度即不通过 |

### 为什么要放在第 3 步而不是第 6 步

判据确认必须在**取数之前**。否则模型先按默认值筛完，再回头问用户"要改吗"，等于让用户为一次已完成的错误判断买单。

## 3. Q4：均播的两条轴

"均播"其实有**两条独立的轴**，不能混：

| 轴 | 取值 |
|---|---|
| **内容形态轴** | 长视频均播 / 短视频均播（用户提到的"长短视频对应均播"） |
| **取值面轴** | score（母本 L552，抽样算术平均）/ drawer（`normalize.js`，中位数）/ list（母本 L724，有界全量池中位数） |

所以登记项要交叉：`avg_views_long.list`、`avg_views_short.list`、`avg_views_long.drawer`……**不是一条"均播"打天下**。

按裁决：**取值面三个都登记，指定一个对外唯一**。

| 取值面 | 出处 | 登记 | 用途 |
|---|---|---|---|
| `score` | 母本 L552（抽样算术平均） | `metric.creator.avg_views.score` | 内部对照，`data_status: unreliable` |
| `drawer` | `normalize.js:144-230`（中位数） | `metric.creator.avg_views.drawer` | 内部查看，`data_status: unreliable` |
| `list_production` | 母本 L724（有界全量池中位数） | `metric.creator.avg_views.list` | **对外唯一口径**，`data_status: reliable` |

对外交付规则：

- 只能引 `list_production`；
- 若用户要的字段只有 `score`/`drawer` 有，交付必须写"该数字为内部口径，不可对外"；
- 同一份交付里出现两种口径 → 校验不通过。

## 4. Q2：P0 覆盖三束（工时 +50%）

原定两束（背调 + 报价），现加**发现**。

| 束 | 先做什么 | 为什么排进 P0 |
|---|---|---|
| 背调 `kol-screening` | 评分卡维度 + 造假判据的问法 | 判据最密 |
| 报价 `kol-negotiation` | CPM 口径 + 价格合理性判断词 | 有可算的数 |
| 发现 `kol-discovery` | 检索词矩阵的"该问什么"、排除规则 v2 | 入口高频，判据靠追问补 |

**影响**：P0 从 2–3 周量级变为 **3–4 周量级**。若想压缩，建议把"发现"降为 P0.5（背调+报价先跑通机制，再加发现），但决策不变，只调顺序。
