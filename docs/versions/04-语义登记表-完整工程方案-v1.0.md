## 2. 三类登记项（数据模型）

### 2.1 指标登记 `Metric`

```yaml
id: metric.creator.avg_views_28d
type: metric
label: 均播（近 28 天）
surface: drawer                 # score|drawer|list_production——同一指标在不同取值面口径不同，分别登记
definition: 近 28 天发布视频播放量的中位数（非算术平均）
formula: median(views where published_at >= today-28d)
deps: [mcp.creator.profile, field:videos[].views]
data_status: unreliable         # reliable | unreliable | unknown  ← 新增字段，全仓原本没有
status_reason: 抽屉口径与页面/名单产线口径存在偏差
fallback: 用 videos[].views 自算中位数
owner: 业务-红人组
version: 1.0.0
```

三个硬规矩：
- **一个取值面一条登记**（均播在 score / drawer / 名单产线是三个口径，母本 L552、L724 与 `normalize.js` 抽屉中位数各自不同）；
- `data_status` 是**新字段**，不伪装成复用既有语汇；与 `read-envelope` 的 `dedupOk=false` 建立映射；
- `owner` 必填，无 owner 不入索引。

### 2.2 判据登记 `Criterion`

```yaml
id: criterion.creator.hot
type: criterion
label: 火爆（红人）
applies_to: [intelligence-01, discovery-03]
definition: 以下三条同时满足
terms:
  - {metric: metric.creator.follower_growth_30d, op: ">", value: 0.20}
  - {metric: metric.creator.avg_views_7d, op: ">", value: 500000}
  - {metric: metric.creator.engagement_rate, op: ">", value: 0.05}
threshold_owner: 业务-红人组          # 阈值必须业务签，工程不代拟
status: draft                        # draft 不得用于对外交付
version: 0.1.0
```

### 2.3 表达登记 `Expression`

```yaml
id: expr.kol_list
type: expression
applies_to: [contract:high-performance-video-list]
sections: [概览, 名单, 每条依据, 覆盖率与缺口, 下一步]
required: [数字必须带口径与时间点, 不确定写待确认]
banned: [非常好, 绝对, 肯定没问题, 大概]
version: 1.0.0
```

> 注意层次：交付结构的事实来源是 `contracts#交付件schema`（列 29/必填 13/排序/无数据写法）；`expr` 只登记**语气与禁用词**，不重复定义列。`TRACE_SECTIONS`（`normalize.js:403` 的四段溯源）**不参与**——那是工具返回体的溯源段，不是交付结构。

## 4. 生效机制：三处必经调用

这是全篇的核心——**不依赖模型自觉**。

### 4.1 注入：`skills read` 返回时展开登记项

现有实现：`daniel_cli/corpus.py:389 read_skill()` 生成 skills_read 载荷。
改动：读取切片正文后，解析其中的引用标记（如 `[[criterion.creator.hot]]`），把这些登记项展开成小表附在返回末尾。

```python
# corpus.py 新增纯函数
def ontology_resolve(ids, index):   # ids 来自正文引用标记；index 来自 _ONTOLOGY.json
    return [ {k: index[i][k] for k in ("label","definition","terms","data_status","owner")}
             for i in ids if i in index ]
```

**为什么这条最关键**：模型不读 skill 就不知道该怎么干，所以它绕不开——**读到技能正文的同时就拿到了口径**，不需要额外记得去查。

### 4.2 签名：取数返回值带口径身份

`lib/normalize.js` 对数值字段附带 `metric_id` / `data_status` / `corpus_version`。模型引用“均播”时，返回值里已写着 `unreliable`——不需要模型自己判断该字段可不可靠。

### 4.3 门禁：交付前本地校验

`daniel playbook validate`（离线自检，已存在）新增检查：
- 交付里每个数字是否带口径与时间点；
- `data_status=unreliable` 的指标是否标注；
- 命中禁用词；
- 必填段是否齐；
- 正文引用的登记项是否都在索引里。

不通过 → 返回缺陷清单 → 模型改 → 重校验（≤3 轮）→ 仍不过则如实标“未达标项”。

## 5. 完整工作流（用户给一句话需求起）

| # | 发生什么 | 调什么 | 登记表做什么 |
|---|---|---|---|
| 1 | 用户说需求 | — | — |
| 2 | 判断走哪束 | `daniel_skills_list` | — |
| 3 | 模糊先问 | `daniel_clarify` | — |
| 4 | 读能力正文 | `daniel_skills_read(skill)` | ★ 展开登记项附在返回末尾 |
| 5 | 取数 | `brands_list`/`kol_profile`/`roster_search`/`daniel_run` | ★ 数值字段带 metric_id + data_status |
| 6 | 判断与筛选 | 模型推 | 按第 4 步拿到的阈值 |
| 7 | 写操作 | `daniel_write_plan` → 确认 → `daniel_write_commit` | 写前置约束校验 |
| 8 | 交付前 | `daniel_run(["playbook","validate"])` | ★ 口径/禁用词/段/引用四查 |
| 9 | 不通过 | 返回缺陷 | 改 → 重校验 |
| 10 | 交付 | — | 落 corpus_version + 登记表版本 |

### 失效场景与兜底

| 场景 | 抓住它的位置 |
|---|---|
| 读了 skill 但按自己理解判 | 第 8 步：数字无口径 / 结论缺证据 → 不通过 |
| 跳过 skill 直接取数 | 第 8 步：登记项引用为空 → 不通过 |
| 引用 unreliable 却当确定值 | 第 5 步字段已带 status，第 8 步查标注 → 不通过 |

**边界要说清**：判断本身对不对，机器校验不了。登记表保证的是“判据统一、口径可查、结构一致”，判断质量靠一致性测试与人复核。

## 10. 度量（先测基线，不预设数字）

- **任务集**：只用**只读工序白名单**（94 条里排除写链）；
- **对比**：强/中/弱三模型 × 每任务 N≥2 次；
- **记账**：MCP 抖动导致的重跑**单列**，不计入分母；重试上限写死；
- **四个数**：数字一致率、登记项引用率、结构合规率、禁用词命中率；
- **验收线是“强弱差距”**：先测现状基线，再定收敛目标（此前写的 90/50 是无出处估值，废弃）。

## 11. 防腐化

| 风险 | 处置 |
|---|---|
| 母本与登记双写 | 母本正文不许写具体阈值（阈值只在登记项）；CI 检查 |
| 手改索引 | `_ONTOLOGY.json` 是生成物，段三自守 sha |
| 无人认领 | `owner` 必填，无 owner 不入索引（C19-d） |
| 过度建模 | 只做被工序/契约引用的；90 天未引用标 `unused` |
| 废弃 | `deprecated` → 双跑 2 周 → 移除 |
