# Daniel Bot 语义层（Ontology）设计方案 v0.2

> **v0.2 变更**：把核心目标从「口径统一」提升为「**表现统一**」——同样任务，在不同 Agent／不同模型上，从执行步骤、思考链路到说话风格都要落在一个可控区间内。语义层因此不只存概念与指标，还存**输出契约**与**推理契约**。
>
> 状态：待评审，不含实施排期。
> 关联：`01-目的优化提案与需求示例清单.md`、`02-填充稿-综合场景需求示例.md`、产品文档 §4.1 当前卡点。

---

## 0. 一句话

> Daniel Bot 现在的质量**只有上限、没有下限**：模型强一点结果就好，弱一点就散。语义层的作用是把「怎么定义、怎么算、怎么走、怎么说」从模型的自由发挥里收回来，**让最弱的那个模型也能达到可交付的下限**。

---

## 1. 问题的本质：波动来自"没有约束的自由"

同一句需求「帮我找一批测评红人」，现在会得到什么，取决于：

| 变量 | 影响 |
|---|---|
| 模型能力 | 强模型会自己补判断标准，弱模型照着字面做 |
| Agent 框架 | 有没有记忆、上下文长短、能不能多轮 |
| Skill 版本 | 提示词写法不同，理解就不同 |
| 环境与上下文 | 同一个词在不同项目里含义不同 |

结果：**上限很高、下限很低**，且不可预测。这不是模型问题——**是把判断权交给了模型**。

一条产品级的线应该是：**判断权在系统里，模型只负责执行与表达。**

---

## 2. 要统一的是三件事，不是一件

| 层 | 统一什么 | 不统一的后果 | 靠什么约束 |
|---|---|---|---|
| **结果一致** | 概念定义、指标口径、数字来源 | 同一红人两个 agent 算出两个"均播" | Metric / Concept 对象 + `data_status` |
| **过程一致** | 执行步骤、判断顺序、何时停下来问人 | 有的跑完才告诉你它跳了步，有的压根没做背调 | **推理契约**（步骤 + 必填证据） |
| **表达一致** | 交付结构、说话风格、禁用表述 | 一份像报告、一份像聊天记录；同一个结论两种说法 | **输出契约**（结构 + 语气 + 黑名单） |

**只有第一件事，产品仍然不稳**：口径对了，但有的 agent 只给结论不给证据、有的把"可能"说成"确定"、有的把三页压成三行。所以后两件事必须和口径一起进这一层。

---

## 3. 三层约束怎么落地

### 3.1 结果一致 → 指标与概念对象

沿用 v0.1 设计：`Concept / Metric / Relation / Constraint / Evidence` 五类对象，其中 Metric 带 `data_status`（reliable / unreliable / unknown）把"均播不准"这类事实写进模型，交付时必须带标注。

### 3.2 过程一致 → 推理契约（ReasoningContract）

不是让模型"写出思考过程"（那是散文，无法校验），而是规定**必须走完的步骤**，并逐步留下结构化痕迹：

```yaml
id: logic.outreach.screen_kol
type: reasoning_contract
applies_to: [task.screen_kol, task.build_list]
steps:
  - id: s1_parse
    required: 明确对象、市场、预算档位、时间要求；缺任何一项必须先追问
    gate: ask_before_proceed
  - id: s2_criteria
    required: 把筛选条件翻译成可计算指标（引用 metric id），不许用形容词
    evidence: [metric.*]
  - id: s3_search
    required: 检索式矩阵 ≥3 组，注明每组预期命中
    gate: show_before_execute
  - id: s4_screen
    required: 逐条给排除理由（引用 constraint id）
  - id: s5_deliver
    required: 名单 + 每条的依据 + 覆盖率说明
forbidden:
  - 跳过 s2 直接检索
  - 用"感觉很合适"作为唯一理由
```

**关键设计：`gate`**——`ask_before_proceed` / `show_before_execute` 把"什么时候必须停下来找人确认"从模型的自觉变成契约条款。这正是访谈里"黑盒顾虑"的直接解药。

### 3.3 表达一致 → 输出契约（OutputContract）

```yaml
id: output.kol_list
type: output_contract
sections: [概览, 名单, 每条依据, 覆盖率与缺口, 下一步]
tone:
  - 结论先行，一句一条
  - 数字必须带口径与时间点
  - 不确定的写"待确认"，不写"应该"
length: 概览 ≤5 行；每条依据 ≤2 行
banned: [「非常好」「绝对」「肯定没问题」「大概」]
required_trace: [s1_parse, s2_criteria, s3_search, s4_screen, s5_deliver]
```

`banned` 不是文风洁癖——**含糊词是把"没判断"伪装成"判断"**，也是最容易在跨 agent 之间产生分歧的地方。

## 4. 怎么让它在任何 Agent 里都生效

这是全篇最关键的一节：**约束必须有执行机制，否则又回到"靠模型自觉"**。

| 机制 | 做法 | 解决什么 |
|---|---|---|
| **① 开工前置** | 任何任务先调 `describe_task(task_type)`，拿到三份契约（结果/过程/表达）再动手 | 防止"不知道标准就开工" |
| **② 交付前校验** | `validate_deliverable(草稿, task_type)` 返回：缺哪些段、哪些数字没带口径、踩了哪些禁用词、漏了哪些步骤 | **把一致性变成可测**，而不是靠人抽查 |
| **③ 不通过就返工** | 校验不过 → agent 自己改 → 再校验（最多 N 轮）；仍不过则如实交付"未达标项" | 让弱模型也有收敛路径 |
| **④ 版本留痕** | 每次交付记录 `ontology_version` + `logic_version` + `output_version` | 事后能回答"这份报告按哪版标准做的" |

**②是重点**：它把"表现统一"从口号变成了一次可执行的自检。任何模型，只要肯跑这一步，就能被拉到同一个下限上；模型再强也不能随意跳段，因为它过不了校验。

> 强制力分阶段：P0 在插件内置工具里做 `validate_deliverable`（最容易加，且是主推形态）；P1 再往 MCP/CLI 铺；硬门（无契约拒绝取数）放到 MCP 稳定性问题解决之后。

## 5. 一致性怎么度量（不然没法验收）

固定一组 **20 个任务集**（覆盖 检索/背调/报价/名单/报告 五类），分别在 **强 / 中 / 弱** 三个模型上跑，看四个数：

| 指标 | 定义 | 目标 |
|---|---|---|
| **数字一致率** | 同一任务关键数字（数量、比例、金额）跨模型一致的比例 | ≥ 95% |
| **步骤完整率** | 契约要求的步骤实际走完的比例 | ≥ 95% |
| **结构合规率** | 交付物段数与必需段齐全的比例 | 100% |
| **禁用词命中率** | 出现 banned 表述的交付占比 | ≤ 5% |

**真正的验收线不是"强模型多好"，而是「强模型与弱模型的差距」**：

> 现状预估：强模型 90 分、弱模型 50 分（差距 40）。
> 目标：强模型 90 分、弱模型 75 分（差距 15）——**下限抬起来，上限不必压**。

这条可以直接写进产品指标：**模型无关性（model-agnostic floor）**。

## 6. 对象模型（v0.2 增补）

| 类型 | 作用 | 关键字段 |
|---|---|---|
| Concept / Metric / Relation / Constraint / Evidence | v0.1 已有，管"结果一致" | 见 v0.1 |
| **ReasoningContract** | 管"过程一致" | steps / gates / forbidden / evidence 要求 |
| **OutputContract** | 管"表达一致" | sections / tone / length / banned / required_trace |
| **TaskType** | 把上面五类串起来的入口 | id / 适用契约 / 典型需求样例 |

`TaskType` 是新加的枢纽：agent 接到需求先判类型，再由类型拿到三份契约。**不需要模型自己判断"该用哪些标准"。**

| # | 接触点 | 改什么 |
|---|---|---|

| 5 | **交付物** | 页脚落三版本号；未达标项单列 |

## 8. 维护与迭代（防腐化）

| 机制 | 做法 |
|---|---|
| 源文件 | git 里的 YAML（`concepts/ metrics/ logic/ outputs/`），一对象一文件 |
| 责任 | 每个 metric / contract 必须有业务 owner；无 owner 不许上线 |
| 变更 | PR + owner 审批 + 语义版本（改定义 = major） |
| 防双写 | CI 禁止 skill 正文出现具体阈值与步骤顺序（出现即报错） |
| 漂移检测 | ① 20 任务 × 3 模型一致性测试进 CI；② `data_status=unreliable` 字段每周抽样回源 |
| 废弃 | deprecated → 双跑 2 周 → 移除 |

## 9. 分阶段

| 阶段 | 范围 | 交付 |
|---|---|---|
| **P0（2–3 周量级）** | 10 个高频指标 + 5 个概念 + **2 份契约**（`logic.screen_kol`、`output.kol_list`）+ `validate_deliverable` 落进插件 + 20 任务基线测量 | 能跑通"一个任务、三个模型、结果可对比" |
| **P1** | 补齐 报价/背调/报告 三类契约；关系层；一致性测试进 CI | 覆盖主要交付物 |
| **P2** | 硬门票据；自进化（从交付中沉淀新概念，人工审核后入库） | 闭环 |

**为什么 P0 选 `screen_kol`**：它是最高频、跨模块步骤最多、也最容易看出模型差异的任务——用它验证"能否把弱模型拉到下限"，最有说服力。

---

## 10. 验收标准

| # | 判据 | 测法 |
|---|---|---|
| 1 | 弱模型达到下限 | 20 任务集在弱模型上：结构合规 100%、步骤完整 ≥95%、数字一致 ≥95% |
| 2 | 强弱差距收敛 | 强弱模型综合分差距 ≤15（现状预估 40） |
| 3 | 可追溯 | 任取一份交付，能查到三个版本号与每个指标的 `data_status` |
| 4 | 无绕过 | `validate_deliverable` 在插件里强制调用；抽检未校验交付 ≤1/20 |

## 11. 风险与「不做什么」

| 风险 | 处置 |
|---|---|
| 契约写太细，把 agent 变成机器人 | 只约束"结论、步骤、结构、语气"，不约束措辞；允许在契约内自由发挥 |
| 校验变成形式主义（agent 走过场） | 校验项必须能对应到内容（如"每条依据引用 constraint id"），不接受空话 |
| 契约与 skill 双写 | CI 双向检查：skill 不许写阈值，契约必须被至少一个 skill 引用 |
| 抬下限压掉上限 | 校验只做"不达标打回"，不做"超出就打回"；强模型仍可写得更好 |

**明确不做**：不做数据仓库、不做指标计算引擎、不做权限系统、不自动改写业务定义（自进化只到"提议"）。
