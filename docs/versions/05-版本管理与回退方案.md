# Daniel Bot 插件 · 版本管理与回退方案

> 触发：语义登记表改造要在现有插件包上动刀，必须保证「改造不符合预期时，回退只换一个包」。
> 状态：待评审（未实施）

---

## 0. 先纠正一个前提：现在的回退**做不到"换个包就行"**

实测当前状态（2026-10-29）：

| 项 | 实际 |
|---|---|
| 安装形态 | **软链到源码目录**：`~/.dsh/profiles/{web,desktop}/node_modules/daniel-dsh-plugin → ../../Desktop/DeepSeek Harness/daniel-dsh-plugin` |
| 版本 | `package.json` = **0.9.11** |
| 版本历史 | **没有 git 仓库**（`git rev-parse` 报 not a repository） |
| 打包产物 | 存在 `daniel-dsh-plugin-0.9.11.tgz` 等一串 tgz，但**当前运行的不是 tgz，是源码目录** |

由此两个结论：

1. **"替换插件包"不会生效**——因为客户端加载的是软链指向的目录，不是 tgz；
2. **现在也无法回退**——没有 git、没有基线快照，改造一旦写进 `daniel-dsh-plugin/`，旧状态就没了（只能靠 tgz 重装，且要先改掉软链）。

所以版本管理方案的第一件事不是"写版本说明"，而是**先造出可回退的基线**。

版本号规则（沿用现有习惯）：

| 变更类型 | 版本位 | 例 |
|---|---|---|
| 加能力 / 改行为 | minor | 0.9.11 → **0.10.0** |
| 只修 bug / 改文案 | patch | 0.10.0 → 0.10.1 |
| 破坏性变更（改工具签名、删字段） | major | 0.10.x → 1.0.0 |

## 2. 采用哪种方式：git 本地仓库 + 目录归档

不推远端（beta 阶段），但本地建 git 便于回溯与后续 push；同时保留目录归档做**不依赖 git 的冷备份**。

```
DeepSeek Harness/
├── daniel-plugins/                        唯一版本根目录
│   ├── 0.9.11/                            现行版（main，tag v0.9.11）
│   ├── next/                              改造版（feat/ontology-registry）
│   └── _archive-0.9.11/                   冷备份（不依赖 git）
├── daniel-dsh-plugin -> daniel-plugins/0.9.11   兼容软链
└── daniel-dsh-plugin-0.9.11.tgz           打包留档
```

### git 基线（2026-10-29 建立）

| 项 | 值 |
|---|---|
| 仓库位置 | `daniel-plugins/0.9.11/.git`（`next/` 为其克隆，独立分支） |
| 默认分支 | `main` |
| 基线提交 | `7b955c8`（baseline: 0.9.11） |
| 标签 | `v0.9.11` |
| 跟踪文件 | 202（忽略 `.DS_Store`／`__pycache__`／`node_modules`／`*.tgz`） |
| 是否进包 | **不会**——`package.json` 的 `files` 白名单不含 `.git` |
| 远端 | 无；后续 `git remote add origin <url> && git push -u origin main --tags` |

### 目录归档（冷备份，已完成）

| 项 | 结果 |
|---|---|
| 归档位置 | `daniel-plugins/_archive-0.9.11/` |
| 文件数 / 体积 | 211 / 5.3 MB |
| 完整性 | `lib/index.js`、`package.json`、`_MANIFEST.json` 的 sha 与源逐字一致 |

### 切版与回退

| 动作 | 命令 |
|---|---|
| 切到改造分支 | `cd daniel-dsh-plugin && git checkout feat/ontology-registry` |
| **回退（方式一：git）** | `cd daniel-dsh-plugin && git checkout v0.9.11` |
| **回退（方式二：冷备份）** | `ln -sfn ".../daniel-plugins/_archive-0.9.11" ~/.dsh/profiles/{web,desktop}/node_modules/daniel-dsh-plugin`（需写 `~/.dsh`，通常要放宽权限） |
| 生效 | 完全退出客户端再打开 + 新开会话 |

两种回退互不依赖：git 坏了走冷备份，冷备份丢了走 git。

### 本地管理的四条纪律

1. **基线不就地改**：改造在分支上做，`main` 永远等于 0.9.11；
2. **每次发版必打包 tgz**，与归档目录并存；
3. **没有 `versions/VERSION-<x>.md` 不算一个版本**；
4. **回退必须跑三条验收**（见 §4）。

> 版本索引见 `VERSIONS.md`。

## 3. 每个版本必须有一份版本说明

命名：`VERSION.md` 放在包根（随包走），另在 `docs/marketing/daniel-bot/versions/` 留一份索引。

## 4. 回退要能验，不是"应该能"

回退后必须跑三条验收（与首次安装同一套）：

| # | 让它做什么 | 期望 |
|---|---|---|
| 1 | 查登录状态 | 已登录 + 掩码账号 |
| 2 | 列能力清单 | 8 个能力域 |
| 3 | 列 3 个品牌 | 真实品牌名 |

> 只回退不验收 = 没回退。尤其注意第 3 条：如果新版的语料/索引残留，可能前两条正常、第三条暴露问题。

---

## 5. 与语义登记表方案的关系

| 项 | 关系 |
|---|---|
| 改造期间 | 客户端跑 0.9.11，开发在 `-next` 或分支，**用户侧零风险** |
| 验证期 | 软链切到新版，出问题**一条命令切回** |
| 语料版本 | 改造会升 `corpus_version`（0.9.204 → 0.9.205），回退时要连语料一起回退（tgz 里带语料，所以换包即回退语料） |
| 交付物 | 新版交付会多「本次筛选维度/未筛维度/口径确认」三行，旧版没有——**回退后历史交付不可与新交付直接比** |
