# 一、为什么要做 Daniel Bot：让 Agent 把营销任务跑完，人只负责判断与拍板

<callout emoji="🎯">
Daniel 提供能力与数据；**真正难的是把一件复杂营销任务从头跑到尾**——流程繁琐、模块之间来回搬、同一批动作还只能一个个来。
Daniel Bot 把「跑」这件事接过去：**Agent 负责跑完，人只负责判断与拍板**。
</callout>

## 1.1 入口变了：从「人操作系统」到「人把任务交给智能体」

真正吃掉时间的不是判断，而是**人必须亲手去操作系统**——填表单、切模块、反复点击、来回核对。

| 环节 | 今天：人以「系统」为中心 | 转变之后：人以「Agent」为中心 |
|-|-|-|
| **需求表达** | 人先想清楚"在系统里怎么落地"，再去找对应模块与页面 | 人只说清**要什么**：目标、对象、条件、可接受的产出 |
| **操作落地** | 人逐个表单填写、逐屏点击、模块之间来回切换 | **Agent 完成**：表单输入、模块操作、数据收集、流转与写入 |
| **中间确认** | 人盯着每一步、怕漏怕错，注意力被切碎 | 只在关键节点被叫住：**看方案、看影响范围、看将被改动的对象** |
| **结果判断** | 人从系统里导出数据，再自己核对 | 人只判断**结果对不对、要不要改**——这才是人该花时间的地方 |

**但只把入口换成 Agent 还不够：Bot 里得真有业务能力。** 只会"调用模块"的机器人，本质是替你点按钮——它不知道什么算合适的红人、报价砍到哪一档算合理、这份名单该不该交出去。三层叠起来才是"懂业务的助手"：

| 分层 | 它负责什么 | 缺了会怎样 |
|-|-|-|
| **能力层（skill）** | 真正的业务理解：7 个阶段、94 道工序的判据与门禁——什么样的人算匹配、什么价算合理、什么数据算注水 | 只会执行"点哪里"，不会判断"该不该" |
| **业务／工序层** | 94 道工序，把判据串成可执行工作流——谁先谁后、每步用哪个口径、哪一步停下来等人确认 | 步骤靠人记，换个执行者结果就变，出错无法复现 |
| **接入层** | 把 Daniel 摸清楚——每个模块对应哪些接口、关键字段、输入输出与限制 | 一动手就踩空：字段对不上、写错对象、该拿的数据拿不到 |

## 1.2 三种形态，当前主推 Agent 插件

| 形态 | 能做什么 | 怎么装 |
|-|-|-|
| **Agent 插件 ★主推** | 整套能力随包内嵌，在客户自己的 Agent 里端到端干活；写操作强制两段式 | 添加插件 → 重启 → 登录一次 |
| 命令行（CLI） | 89 条命令 / 22 个模块，适合自动化与脚本；写入四道闸 | 一条命令装完 |
| MCP | 只接数据面，不出交付物；写操作只出确认单、永不执行 | 写一条配置 |

三种形态共用同一套能力：**8 项能力**（总纲与路由、红人发现、深度背调、外联 pitch、报价谈判、合同出具、执行与声量、Daniel 接口工序）、94 道工序、直连 12 个业务模块。

**模块之间也串起来了**：原来 A 模块的结果要人工导出、对表、回填到 B；现在由 Agent 自己取数、对齐字段、回填。同类动作还能并发排队（失败退避重试、可断点续跑），批量发起、统一收口。

一句话：把「围着系统来回点、来回搬」压成「**一次交办 ＋ 几次确认**」，人的时间回到判断与决策上。

# 三、能力边界：什么能交给它，什么先不要

<callout emoji="💡">
**判断标准只有一条**：**规则清楚、数据源固定、结果可核对**的活，交给它；**涉及写入和修改操作、权限变更以及结果标准**的活，人来拍板。
**关于"阶段性确认"**：为了确保工作流的可靠性，防止出现Agent在用户没有感知的情况下自动做决定，所以所有涉及到daniel内的写入操作（新增，编辑，删除）都会自动暂停等待用户确认后执行
</callout>

| 可以直接交给它 | 原因 |
|-|-|
| 跨模块取数与汇总（品牌/名单/提及/声量/情报） | 数据源固定，结果可回读核对 |
| 名单类操作（建名单、导入、合并、去重、按规则剔除） | 规则明确，每一步都能给剔除理由 |
| 背调与真实性核验、受众匹配核验 | 有系统评分与明细，可逐条复核 |
| 按模板出交付件（名单、审核表、视频清单、评估表） | 格式固定，交付前有自检 |
| 写回系统（建品牌、配品类、建活动、维护名单） | 有确认环节：先给方案，人确认后才落库，落库后自动回读校验 |

| 先不要交给它 | 原因 |
|-|-|
| 修改他人账号、工作区权限、成员管理 | 权限类操作风险高 |
| 口径没有共识的新型任务 | 先人定标准，再交给它执行 |

| 🟠 高 | 凭据与账号共享 | 会话有效期一年、存本机；同一台电脑多人轮用或交接时，登录态即身份 | 凭据优先存系统钥匙串；可查看当前账号与来源；多账号可切换 | 明确的使用人↔账号绑定规范；共用机器的操作纪律；更细的审计字段（谁在用） |
| 🟡 中 | 数据合规与敏感信息 | 红人联系方式、报价、合同条款属敏感信息，跨团队／跨境流转需合规确认 | 写操作留痕、结果本地落盘、外发由人决定 | 敏感字段清单与分级；对外交付件的固定脱敏规则 |
| 🟡 中 | 口径漂移 | 宿主改写产出，导致同一指标两套说法；跨版本能力升级也可能改变判断标准 | 工序契约化、出件前自检、计数自洽校验 | 产出模板的唯一真源与"宿主不得改写关键指标"的约定 |

<callout emoji="🎯">
**结论（当前优先级）**：**系统权限 ＞ 语料脱敏 ＞ 并发配额 ＞ 凭据共享 ＞ 口径漂移**。
</callout>

两项 🔴 都是"**扩大使用范围之前必须先处理**"的：一个是**能改坏数据**，一个是**会把内部经验带出去**。

## 4.1 当前卡点

| 卡点 | 现状 | 对使用的影响 |
|-|-|-|
| **MCP 层不稳定** | 调用链路还不够稳，偶发失败需要重跑 | 连续多步任务可能中断，得从头再来；暂不建议把它当成无人值守的生产链路 |
| **字段准确性** | 部分字段尤其是**均播**这类派生指标，取回值与实际有偏差 | 这类数字**不能直接对外汇报**，交付前必须回源核对或标注口径 |
| **授权链路未自动化** | 插件包接入后，登录还不能自动完成：还需要用户自己去浏览器缓存里取出对应的 session 值、复制给 Agent，才能完成授权登录 | 首次使用与换机时多一步手工操作，业务同学容易卡在这一步；这也是「零门槛接入」还没做到的地方 |

> 三条的定位不同：前两条影响「数字能不能直接用」，第三条影响「接入有多费事」。前两条靠交付前回源核对兜住，第三条靠一次性取 session 值解决（有效期一年）。





# 五、用户访谈反馈（荣荣、Doria）

访谈对象：荣荣、Doria。三条反馈集中在同一件事：**自动化过程能不能看清、敢不敢用**。

## 5.1 对自动化工作流有「黑盒」顾虑

尤其是**综合类需求的流程全自动化**：中间节点对应的输出结果是否可用、到底做了什么、按什么逻辑判断——这些担心**无法追溯**。

> **改进方向（重点）**：优化执行过程中的交互信息展示，把**结论对应的思考链路 ＋ 证据链路**补全——让人能看到「这一步做了什么、依据是什么、为什么这么判」。

## 5.2 提示信息与风险预警希望更前置

面对**模糊需求**时，期望能主动给出**额外的追加提问或风险提示**，例如：如果想要更准确的结果，需要再补充一些 xxx 的补充信息。

## 5.3 自动搜索结果的准确性

自动搜索出来的结果到底准不准、可不可用——这是他们最直接的疑问。

# 六、后续规划：从「接进来的能力」到「真正懂营销的项目指挥官」

> 现状是**能力供给形态**：能力与接口齐备，但"谁来编排、产出是否受控"交给了接入方。要走到"一个真正懂营销业务的 Daniel 项目指挥官"，先要看清楚**三种交付形态的差别**，再定路线。

## 6.1 四种交付形态对比

| 维度 | 交付 CLI | 交付 MCP | 交付 Agent 插件 ★当前主推 | 交付托管 Agent（下一阶段） |
|-|-|-|-|-|
| **交付物是什么** | 一套可执行命令 ＋ 能力层 | 一组接口，挂进客户自己的 Agent | **一个装进客户 Agent 的插件包**（能力随包内嵌：工序 ＋ 12 模块读写 ＋ 出件） | 一个托管在服务端的"项目指挥官" |
| **用户动作** | 装命令行、配 PATH | 配一条 MCP 配置 | **添加插件 → 登录一次 → 在自己 Agent 里下任务**（三步） | 给目标，平台代跑 |
| **谁在编排** | 使用方 Agent（每次现编） | 客户自己的 Agent | 客户自己的 Agent，但**被插件内的工序与判据约束** | 我方（工序、判据、角色内建） |
| **产出可控性** | 中 | **低**（调用顺序与次数不受控） | **较高**：关键动作走两段式（先给计划、人确认后执行） | 高 |
| **写操作** | 能执行（四道闸） | 只出确认单、不执行 | **能执行，但必须两段式**：计划 → 人确认 → 执行 → 回读 → 审计 | 能执行（服务端统一审批） |
| **接入成本 / 体验一致性** | 高 / 差 | 中 / 差 | **低 / 较好**（一次装包即得完整能力；各宿主体验趋同） | 最低 / 最好 |
| **可治理性（权限·配额·审计）** | 中（本机约定） | 低 | **较高**（写判定与留痕随插件下发；配额治理待服务端化） | 高（集中鉴权与配额） |
| **升级与运维** | 每台机器各自升级 | 客户环境各自配置 | **插件升级即能力升级**（能力随包内嵌，版本一处管理） | 一处升级，所有人受益 |
| **适合的能力类型** | 内部技术用户、自动化脚本 | 工具类、设计类、风格类（单点） | **业务编排类：多模块协作 ＋ 多步工序 ＋ 要交付物** | 规模化/统一体验的业务 |
| **主要风险** | 体验参差、能力被误用 | 产出漂移、无法审计调用 | **能力语料随包外发**（须分级脱敏）；宿主差异 | 依赖服务端身份与运维 |



## 6.2 必须先补齐的五件基础设施（对应第四节「风险清单」）

| # | 必须先解决 | 对应风险 |
|-|-|-|
| 1 | **统一身份与权限**：不靠单机凭据，账号与企业权限体系打通 | 🔴 系统权限 ／ 🟠 凭据共享 |
| 2 | **写操作的量级治理**：单任务变更上限、批量前快照、连续写约束 | 🔴 系统权限 |

| 4 | **并发与配额治理**：全局预算、跨任务排队、额度可见 | 🟠 并发与配额 |
| 5 | **产出口径唯一真源**：模板与指标定义集中管理，宿主不得改写关键指标 | 🟡 口径漂移 |
